# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Waypointer (branded "Sulla Via" in the frontend UI — `frontend/index.html`'s `<title>` and `App.tsx`'s header — but the repo, Python package (`pyproject.toml`'s `name = "waypointer"`), and all module paths keep the original name; this was a branding-only rename) is a web app: a visitor uploads a GPX route, the backend finds OpenStreetMap points of interest near it via the Overpass API (one query per requested POI type — see "POI types" below — at a user-configurable per-type max distance), the visitor reviews/selects them on a map + checklist, and downloads a new route file with the selected POIs added — either as GPX waypoints (generic devices) or as a FIT course file (Wahoo ELEMNT ROAM v3, so each POI's icon renders correctly while navigating; see `fit_io.py` below for why this needs a whole separate code path). A visitor can also connect a Wahoo account (OAuth) to push a route straight to their Wahoo app, or import a route they already have there.

Two halves in one repo, one Docker image:
- **Backend**: `src/waypointer/` — stateless FastAPI app (Python, managed with `uv`).
- **Frontend**: `frontend/` — React + TypeScript SPA (Vite, shadcn/ui, react-leaflet), built to static assets that the backend serves.

## Commands

### Backend
```bash
uv sync                                          # install deps
uv run pytest                                    # run all tests
uv run pytest tests/test_fit_io.py                # run one test file
uv run pytest tests/test_fit_io.py::test_build_course_fit_bytes_round_trip   # run one test
uv run uvicorn waypointer.main:app --reload      # dev server at :8000
```

### Frontend
```bash
cd frontend
npm install
npm run dev       # Vite dev server at :5173, proxies /api/* to localhost:8000 (see vite.config.ts)
npm run build     # tsc -b && vite build -> frontend/dist/
npm run lint       # oxlint
```
Run the backend (`uv run uvicorn ... --reload`) and `npm run dev` side by side for frontend work — the Vite proxy forwards API calls, so no CORS setup is needed. `uv run uvicorn` alone (no Vite) only serves the frontend correctly if `frontend/dist/` already exists from a prior `npm run build`; otherwise the catch-all mount in `main.py` is skipped entirely (see below) and only `/api/*` routes work.

### Docker (production shape)
```bash
docker build -t waypointer .
docker run -p 8000:8000 waypointer
```
Multi-stage: a `node` stage runs `npm ci && npm run build`, then the `python:3.11-slim` + `uv` stage copies that build output in. The only production deployment target is a Raspberry Pi 5 on the LAN, run via `docker-compose.yml` (below) — there is no cloud/PaaS deployment.

For local (LAN) use, `docker-compose.yml` wraps the same image build — `docker compose up --build -d` (reads a `.env` file in the repo root for the vars below automatically).

#### Remote access & TLS (Raspberry Pi)
The Pi is reached from outside the LAN via a [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/) (`cloudflared`, run separately from this repo — not one of the containers in `docker-compose.yml`), which forwards a public hostname to the app's published port. Cloudflare terminates TLS at its edge and proxies plain HTTP to the container, so `SSL_KEYFILE`/`SSL_CERTFILE` are unset in normal operation and `docker-compose.yml` publishes the app on host port `${PORT:-8000}` — no reverse proxy or cert management needed on the Pi itself for the tunnel path.

`uvicorn` can still terminate TLS directly when `SSL_KEYFILE`/`SSL_CERTFILE` are set — this is an opt-in fallback for browsing the app directly over the LAN without going through the tunnel (e.g. straight to the Pi's mDNS hostname), not the primary access path. Generate a self-signed cert once on the host if you want this (SAN must match how you'll browse to it):
```bash
openssl req -x509 -nodes -newkey rsa:2048 \
  -keyout waypointer.key -out waypointer.crt -days 825 \
  -subj "/CN=sampi.local" \
  -addext "subjectAltName=DNS:sampi.local"
```
Set the cert env vars via a `.env` file next to `docker-compose.yml` (never bake a private key into the image):
```bash
# .env
SSL_KEYFILE=/certs/waypointer.key
SSL_CERTFILE=/certs/waypointer.crt
CERTS_DIR=/home/pi/waypointer-certs   # host dir holding the cert/key generated above
```
then `docker compose up --build -d`. Each browser/device will show a one-time self-signed-cert trust warning on first visit over this LAN-direct path.

Whichever origin a visitor actually uses — the Cloudflare tunnel's public hostname (the normal case) or the LAN-direct address above — needs `<origin>/wahoo-callback.html` added to the registered redirect URIs in the Wahoo developer dashboard: the redirect URI is derived from `window.location.origin` (`frontend/src/lib/wahooAuth.ts`), and Wahoo requires an exact string match, so a registered URI missing the actual port (or carrying one that isn't actually there) fails with a misleading error (see [[project_wahoo_oauth_redirect_uri]]).

### Telemetry (Prometheus + Grafana + node_exporter)
Three extra `docker-compose.yml` services, LAN-only, no auth beyond Grafana's own login — the app itself has no login either, relying on Cloudflare's edge (or the Pi's LAN, for anyone with physical/network access) rather than in-app auth; see "Remote access & TLS" above. Not part of the Docker image itself — `waypointer` stays a single-responsibility container; telemetry is bolted on at the compose layer so `docker run waypointer` (no compose) still works standalone.

- **App metrics**: `prometheus-fastapi-instrumentator` is wired into `main.py` right after `app = FastAPI(...)`, exposing `GET /metrics` (request counts, latency histograms, in-progress gauge, all labeled by method/path/status). Single uvicorn process — the default in-memory `prometheus_client` registry is fine, no multiprocess mode needed (same reasoning as `rate_limit.py`'s in-process design).
- **Host metrics**: `node-exporter` mounts `/proc`, `/sys`, `/` read-only (remapped under `/host/*` with matching `--path.*` flags, the standard node_exporter compose convention) plus `pid: host`, to report real host-level CPU/mem/disk/temp rather than the container's own cgroup — temperature comes from the `hwmon`/`thermal` collectors automatically off the mounted `/sys`, no extra flag needed on modern Raspberry Pi OS kernels. Not published on a host port — only reachable from `prometheus` over the internal `waypointer-net` network.
- **Scrape config**: `monitoring/prometheus.yml` (bind-mounted read-only into the `prometheus` container) lists two jobs — `waypointer` (`waypointer:8000/metrics`) and `node` (`node-exporter:9100/metrics`) — by compose service name, not `localhost`, since Prometheus runs in its own container on the same bridge network. The normal case is plain HTTP (TLS handled externally by the Cloudflare Tunnel — see "Remote access & TLS" above), which is what this file defaults to. If you instead enable `uvicorn`'s own TLS via `SSL_KEYFILE`/`SSL_CERTFILE` for LAN-direct access, the `waypointer` job's `scheme` must be changed by hand to `https` (keeping `insecure_skip_verify: true` for the self-signed cert) — this isn't automatic, since Prometheus's static config can't react to another service's env vars.
- **Persistence**: `prometheus` and `grafana` use named Docker volumes (`prometheus-data`, `grafana-data`), not host bind-mounts — simpler to manage on the Pi, survives `docker compose down` (not `down -v`). Prometheus keeps its default 15-day retention — no tuning needed for a single-Pi personal deployment.
- **Grafana datasource**: auto-provisioned via `monitoring/grafana/provisioning/datasources/prometheus.yml` (Grafana's declarative provisioning mechanism), pointing at `http://prometheus:9090` — so Grafana has its Prometheus datasource wired up with zero manual UI clicking on first boot. Dashboards themselves are not auto-provisioned — build/import panels manually (e.g. the community node_exporter full dashboard, id `1860`, plus a hand-built panel over the `http_request_duration_seconds` histogram for app latency).
- **Access**: Grafana at `http://<pi-host>:${GRAFANA_PORT:-3000}` (default login `admin`/`${GRAFANA_ADMIN_PASSWORD:-admin}` — change the password via the Pi's `.env` file, since this is the only credential gate anywhere in this stack), Prometheus's own UI at `http://<pi-host>:${PROMETHEUS_PORT:-9090}` (useful for checking scrape target health under Status > Targets before debugging in Grafana).

## Backend architecture (`src/waypointer/`)
Four endpoints, all stateless — no DB, no session, no server-side memory between requests. The frontend holds all state client-side and resubmits the original GPX file on every request.

- `main.py` — `POST /api/find-pois`, `POST /api/save`, `POST /api/wahoo/route-payload`, `POST /api/wahoo/import-route`. Also mounts the built SPA (`frontend/dist/`, `StaticFiles(html=True)`) at `/` as a catch-all — **this mount must stay the last thing registered in the file**, after every API route decorator, or it shadows `/api/*` entirely (Starlette matches routes in registration order). The mount is skipped if `frontend/dist/` doesn't exist, so backend-only dev without a frontend build doesn't crash on startup.
  - `find_pois` builds one Overpass query per requested POI type up front (still 400s on an unknown/non-searchable `poi_type` before any Overpass call fires), then fires them all **concurrently** via `asyncio.gather` over `asyncio.to_thread(query_overpass, ...)` wrappers, each catching `OverpassError` independently. One type failing doesn't take the others down: it returns 200 with partial `candidates` plus a `failed_poi_types: list[FailedPoiType]`, and only 502s if *every* requested type failed. The frontend actually calls this once per POI type anyway (see frontend section), so per-request concurrency mostly matters when a caller batches several types into one `poi_config`.
  - `save` and `wahoo_route_payload` share `_build_fit_course_points`, which merges newly-selected candidates with kept (non-discarded) pre-existing waypoints into one FIT course-point list — each kept waypoint's type comes from the `existing_waypoint_types` form field (JSON dict, original-index-as-string → poi_type key, from the visitor correcting `infer_poi_type`'s guess), defaulting to `"generic"`. In `save`'s GPX branch, `_resolve_symbol` (visitor's `symbols` override → the type's `default_gpx_symbol` → its `label`) is applied to kept waypoints *before* `discard_waypoints` runs — ordering matters because `discard_waypoints`/`existing_waypoint_types` both index against the upload's *original* (pre-discard) waypoint order.
  - `wahoo_route_payload` builds the same FIT bytes as `save`'s FIT branch (always FIT, regardless of the visitor's local-download device choice — Wahoo's route push has no GPX equivalent) plus distance/ascent/name metadata for the browser to POST to Wahoo's `/v1/routes`, computed server-side since only the backend ever has the full-resolution, elevation-carrying route (`/api/find-pois` only ships the frontend a simplified, elevation-stripped polyline).
  - `wahoo_import_route` downloads a Wahoo-hosted FIT route server-side (Wahoo's CDN has no CORS headers, so the browser can't fetch it directly) and converts it to GPX via `fit_read.py`, so an imported route re-enters the same GPX-only pipeline as a manual upload. SSRF guard: the caller-supplied `file_url`'s host must equal or suffix-match `WAHOO_FILE_HOST_SUFFIX = ".wahooligan.com"`. No Wahoo access token is sent — the CDN URL is expected to already be publicly fetchable.
- `poi_types.py` — the POI type registry (`POI_TYPES`, not a plugin system, mirrors `device_profiles.py`'s style): ~55 entries today. Most are **not searchable** (`tag_filter=None` — used only to classify pre-existing waypoints via `infer_poi_type` and to pick a FIT icon via `course_point_type`); a `tag_filter` plus `min_distance_m`/`max_distance_m`/`default_max_distance_m` bounds (enforced by `clamp_distance_m`) makes a type Overpass-searchable. Only `water` sets `default_gpx_symbol` (`"Water"`) — every other type falls back to its `label` for the GPX `<sym>` tag. `DEFAULT_VISIBLE_POI_TYPES = ("water",)` is what a fresh browser sees pre-populated (water is the core use case; a visitor adds more via the frontend's "add a POI type" picker) and is also `find_pois`'s fallback when the `poi_config` form field is omitted entirely. `POI_TYPE_BY_COURSE_POINT_TYPE` is the reverse mapping (course_point_type → key), built as a plain dict comprehension because uniqueness is asserted by `test_poi_types.py` against `dev_tools/wahoo_poi_mapping.json`; `fit_read.py` uses it to recover a POI's type from a FIT file without guessing from text. This is the single source of truth for POI types — `frontend/src/lib/poiTypes.ts` mirrors it by hand, same convention as `schemas.py`/`candidate.ts` below.
- `geometry.py` — pure-stdlib haversine/point-to-segment/point-to-polyline distance, and `simplify_rdp` (Ramer-Douglas-Peucker). `simplify_rdp`'s output is used **only** to keep each Overpass query small and for the map's route line — the authoritative "is this POI within range" check in `main.py` always runs against the full-resolution, unsimplified route, using each request's own per-type clamped distance (not a single global constant). Because the simplified route can wander up to `SIMPLIFY_TOLERANCE_M` from the true route, `main.py` pads the *Overpass-side* search radius by that same tolerance — without it, small requested distances (e.g. near a type's `min_distance_m`) can make Overpass's own `around` search miss nodes that the full-resolution check would otherwise confirm are genuinely in range.
- `osm.py` — Overpass QL query builder + HTTP client. Two non-obvious things: (1) Overpass expects the raw query text as the POST body, not wrapped in a `data=` form field — the latter gets rejected with 406 by at least the `overpass-api.de` mirror; (2) a custom `User-Agent` is required or Overpass rejects the default `python-requests` UA (this same `USER_AGENT` constant is reused by `main.py`'s Wahoo FIT download in `wahoo_import_route`). There's also a small in-process TTL cache to avoid hammering the shared public Overpass instance from a public deployment — this cache, not `rate_limit.py`'s counter, is the real protection against hammering Overpass. `build_overpass_query` takes `tag_filter`/`radius_m` as parameters — `main.py` calls it once per requested POI type.
- `gpx_io.py` — GPX parsing/merging via `gpxpy`, operating on bytes only (no filesystem I/O anywhere in the request path). Dedup of previously-added POIs works by stamping a custom `<extensions><waypointer:osm_id>` marker on GPX waypoints and checking for it on re-upload, with a proximity fallback for waypoints that lack the marker (hand-edited files, other tools) — this dedup is POI-type-agnostic, keyed only on OSM id/location. `discard_waypoints(gpx, indices)` removes pre-existing `<wpt>` entries by their position in the *original* upload's waypoint list (see `ExistingWaypoint.index` in `schemas.py`) — it must run before `add_waypoints` appends any newly selected candidates, since indices are only meaningful against the pre-discard order. `infer_poi_type(wpt)` best-effort classifies a pre-existing waypoint, in priority order: (1) a stamped `poi_type` extension marker (written by `stamp_poi_type`, used when the waypoint came from `fit_read.py`) wins outright; (2) else a stamped `osm_id` marker (a waypoint we ourselves previously added) → `"water"` (safe today since water is still the only auto-added type — revisit if that changes); (3) else substring-match the waypoint's `<sym>`/`<type>` text against each registered type's `sym_hints`; (4) else `"generic"`. Deliberately never matches against `<name>` — free-text names cause false positives (e.g. "Water Street Cafe").
- `fit_io.py` — builds a full ridable FIT course (not just isolated waypoints) using the `fit-tool` library. **A POI's icon on a Wahoo does not come from the standard FIT `course_point.type` enum** — reverse-engineering a real Komoot→Wahoo-generated FIT file (see `dev_tools/`) showed the icon is driven by a custom developer field named `course_point_type` (uint8), keyed per POI type in `poi_types.py` (e.g. `16` = water). This was later confirmed against the device for the full 0-99 range (`dev_tools/wahoo_poi_mapping.json`). The native `type` field is left as `CoursePoint.GENERIC` to match the confirmed-working reference file.
- `fit_read.py` — the inverse of `fit_io.py`: parses an existing FIT file (`fit_tool.FitFile.from_bytes`) into GPX bytes, used by `/api/wahoo/import-route`. `RecordMessage`s become one `GPXTrack`/`GPXTrackSegment`; `CoursePointMessage`s become `GPXWaypoint`s, each stamped with its recovered POI type (via the same developer field `fit_io.py` writes, looked up in `POI_TYPE_BY_COURSE_POINT_TYPE`, `"generic"` if absent/unrecognized) so `infer_poi_type` doesn't need to guess on next upload. fit-tool's position getters already return degrees, no semicircle conversion needed. Raises `ValueError` if the file has no positioned track points — a FIT with course points but no track isn't a usable route, and `main.py` surfaces that as a 400.
- `device_profiles.py` — small registry (`DEVICE_PROFILES`, not a plugin system) mapping a device key to just `{name, output_format}` (`GPX` or `FIT`) — two entries, `generic` and `wahoo_elemnt_roam_v3`. The format-specific values this used to hold directly (GPX symbol, FIT course_point_type) have moved into `poi_types.py`'s per-type registry now that POI types number in the dozens, not just water.
- `rate_limit.py` — in-memory per-IP sliding window (`REQUESTS_PER_WINDOW = 60` per `WINDOW_S = 60.0`), applied only to `/api/find-pois`. Sized generously because the frontend fans one "Find POIs" click into one `/api/find-pois` call *per selected POI type* (see frontend section) rather than one combined call — real Overpass call volume per search is unchanged, but this endpoint now gets hit N times instead of once for the same amount of work, so the budget covers a full-registry search (~40 searchable types) plus a couple of re-searches within the window. Single-process only, not meant to survive multiple workers/restarts.
- `schemas.py` — the Pydantic response/request shapes shared with the frontend's TS types: `Candidate` (carries `poi_type`), `PoiSearchConfig` (one entry per requested POI type + its max distance, sent as a JSON-string form field to `/api/find-pois`, same pattern as `/api/save`'s `selected_candidates`), `ExistingWaypoint` (a pre-existing `<wpt>` from the uploaded file, tagged with its `index` in that file's original waypoint list and a best-effort inferred `poi_type` — editable client-side before it affects export), `FailedPoiType` (one requested type whose Overpass call errored, `find_pois` returns a list of these instead of failing the whole request), `FindPoisResponse`, and `WahooRoutePayload` (FIT bytes as base64 + display metadata for a browser-side POST to Wahoo)
  (`frontend/src/types/candidate.ts` mirrors these by hand — keep them in sync manually when changing one side). `/api/save` and `/api/wahoo/route-payload` both accept `discarded_waypoint_indices` (JSON-string, defaults `"[]"`), `existing_waypoint_types` (JSON-string dict, defaults `"{}"`), and an optional `route_name`; `/api/save` alone also accepts `symbols` (JSON-string dict, poi_type → GPX `<sym>` override, defaults `"{}"`). `route_name` is kept separate from the sanitized output filename stem (`_safe_filename_stem` vs `_display_name` in `main.py`) so a user-typed name isn't mangled for filesystem safety before being shown as FIT `course_name`/Wahoo `route[name]`.

`dev_tools/` is exploratory tooling, not part of the shipped app: `generate_test_waypoints.py` builds a FIT file with all 100 `course_point_type` values laid out in a grid for manual on-device icon testing; `wahoo_poi_mapping.json` and `POIs.csv` are the resulting reverse-engineered value→icon mapping (cross-referenced against Strava/RideWithGPS/komoot's own POI category names) — this is the source of truth `poi_types.py`'s `course_point_type` values and `test_poi_types.py`'s assertions are checked against.

## Frontend architecture (`frontend/src/`)

- `App.tsx` owns all cross-cutting state via plain `useState` (no Redux/Context — intentionally, the tree is shallow). `selectedIds: Set<number>` is shared between `RouteMap` (map marker popups) and `CandidateChecklist` (the list) — both are just different views over the same state and call the same `onToggle`, which is what keeps map-popup and checklist selection in sync with no extra glue code. `keptWaypointIndices: Set<number>` is the equivalent for pre-existing waypoints from the uploaded file — defaults to "all kept" on every successful search, and `SaveCard` inverts it (kept → discarded) into the indices it sends to `/api/save`. `waypointTypeOverrides: Record<number, string>` holds the visitor's corrections to `infer_poi_type`'s guess for pre-existing waypoints (indexed by original waypoint index, applied on top of `existingWaypoints` via `useMemo`, survives a later re-search) — wired into both `ImportCard`'s "Waypoints" tab and `RouteMap` via `onChangeWaypointType`; there is no separate "assign waypoint types" dialog component, this is inline per-row editing via `PoiTypeCombobox`. `searchedPoiTypes` snapshots which POI types + distances were actually searched for at find-time, so `CandidateChecklist`'s per-type subsections (and their empty states) don't shift if the visitor tweaks step 2's inputs after results are already showing, without re-running the search. Other cross-cutting state: `wahooTokens` (loaded from `lib/wahooSettings.ts`/localStorage), `mapStyleKey`, `hoveredPoi` (shared hover highlight between map and checklist, `{kind: "candidate" | "waypoint", id}`), `openStep` (accordion-style step-card open/closed state).
  - `handleFind` (the "Find POIs" orchestration) fires one `findPois(file, [entry])` call **per POI-type entry**, not one call carrying every type — staggered by `SEARCH_STAGGER_MS` (200ms) × index, smallest `max_distance_m` first, via `Promise.allSettled`, because firing every request simultaneously made the public Overpass mirror more likely to time out/502 (they still overlap in flight, just not at the same instant). Each type that's unchanged since the last search and didn't previously fail is skipped (`isAlreadySatisfied`, compared against `searchedPoiTypes`), surfacing an "already up to date" toast if nothing needed re-fetching. Results accumulate into a plain mutable object (not React state) pushed into `setFindResult` after each chunk resolves, so the map and checklist fill in progressively per type instead of waiting for the slowest one; a previously-failed or previously-missing type's completion/error status drives `FindPoisCard`'s per-row spinner/check/warning icon and its running `(done+errored/total)` count in the button label.
- `RouteMap.tsx` always renders (a `MapContainer` with a neutral world-view default before any route is loaded) — the map is meant to be persistently visible, not conditionally mounted. Before `/api/find-pois` returns, it shows a route line parsed client-side (`lib/gpx.ts`, via the browser's `DOMParser`, no library) purely for instant visual feedback on import; once the backend responds, it switches to the backend's authoritative `route_coords` + candidate markers. POI candidates render as `Marker`s with an `L.divIcon` built by `lib/mapIcons.tsx`'s `buildCircleDivIcon` — the candidate's `poi_type` is looked up in `POI_TYPES` to pick its icon and color, rendered via `renderToStaticMarkup` into an inline-styled (not Tailwind-class-based, since Tailwind's static content scanner can't see classes assembled inside a template-literal string) colored circle `<div>`, with opacity distinguishing selected/unselected — this is why `L.divIcon`'s `className` must be explicitly set to `""`, overriding `leaflet.css`'s default `.leaflet-div-icon` white-box styling. The route's start/end points get their own non-interactive `Marker`+`Tooltip` (no `Popup`/checkbox) via `RouteEndpointMarkers` — green `Play` icon for start, red `Square` icon for end, collapsed into one combined marker when they coincide (loop/out-and-back routes). `RouteDirectionArrows` overlays arrowheads along the route using the `leaflet-polylinedecorator` plugin (side-effect import, patches the shared `leaflet` module, ships no CSS of its own) — it has no react-leaflet wrapper, so it's integrated imperatively via `useMap()`/`useEffect`, mirroring the existing `FitBounds` pattern in this same file, with layer cleanup in the effect's return to avoid leaking decorator layers across re-renders. Map cartography is switchable via `lib/mapStyles.ts`'s `MAP_STYLES` registry — today just one real style, `road_cycling` (a hand-forked OpenFreeMap "liberty" style at `frontend/public/map-styles/road-cycling.json` that highlights dedicated cycleways and grays out bike-prohibited/unpaved roads), plus commented-out placeholders for other activity types with no custom cartography yet. `MapLegend.tsx` + `lib/mapStyleLegend.ts` derive the legend's colors/labels by evaluating the *actual* style JSON's paint expressions at render time rather than hand-copying colors, so the legend can't drift from the style file.
- Layout is a persistent left-hand map + a right sidebar (`md:w-1/3 md:min-w-[480px]`, not a fixed pixel width) holding collapsible, numbered `StepCard`s (✅-suffixed once complete), in order: `ImportCard` (drag-and-drop or click-to-browse; also a "Waypoints" tab for reviewing/retyping the upload's pre-existing `<wpt>` entries) → `FindPoisCard` (one row per POI type the visitor has added — every listed type is always searched, there's no per-row enable checkbox anymore; types are added via `PoiTypeCombobox`'s "add a POI type" picker and removed via a per-row remove button; columns are grid-aligned regardless of label width) → `CandidateChecklist` (only once results exist; renders one subsection per searched POI type — with its own empty state if that type found nothing — plus, if the uploaded file already had any `<wpt>` entries, an "Already in this file" subsection with a keep/discard checkbox and retype control per one; shared row rendering lives in `PoiListItem.tsx`) → `SaveCard` (device/format selection, route naming via `RouteNameDialog.tsx`, save, and a "send to Wahoo" action, only once results exist). Stacks vertically below the `md` breakpoint instead of side-by-side.
- **Wahoo integration** (`lib/wahooConfig.ts`, `wahooAuth.ts`, `wahooConnect.ts`, `wahooApi.ts`, `wahooSettings.ts`, `components/WahooProfileMenu.tsx`, `WahooRoutesDialog.tsx`) — PKCE OAuth2 public-client flow (no client secret) against Wahoo's API, requesting `user_read routes_read routes_write` scopes (`routes_read` isn't used by anything today, requested pre-emptively for future use; `missingWahooScopeWarning()` checks granted-vs-requested since Wahoo can silently under-grant). `connectWahoo()` opens a popup rather than a full-page redirect, specifically to avoid losing in-progress upload state held in `App.tsx`'s `useState`; it listens for a `postMessage` from `wahoo-callback.html` (present at `frontend/public/wahoo-callback.html`, copied into the build), which is where the `<origin>/wahoo-callback.html` redirect-URI requirement described above comes from. Connect success/failure is observed from `connectWahoo()`'s own promise resolution back in the original tab, not from the callback page itself (which isn't part of the SPA and isn't instrumented). `WahooRoutesDialog` is one shared component driven by a `mode: "import" | "manage"` prop: full-screen listing of the visitor's Wahoo routes, with rename (`RouteNameDialog.tsx`, also reused for pre-save naming) and delete (confirmed via the shadcn `AlertDialog`) in "manage" mode, one-click import in "import" mode — import round-trips through the backend's `/api/wahoo/import-route`.
- `lib/api.ts` — thin typed `fetch` wrappers, one function per backend endpoint, no abstraction beyond that.
- `lib/poiTypes.ts` — hand-mirrors the backend's `poi_types.py` registry (key, label, searchability, default/min/max search distance), plus two frontend-only display fields with no backend equivalent: `icon` (a `LucideIcon`) and `color` (the marker/popup color for that type) — mirrors the full ~55-entry registry, not just water. `PoiTypeCombobox.tsx` (a `Popover` + `cmdk` `Command` searchable combobox) exists specifically because that entry count is too many for a plain `<Select>`; it's used both for `FindPoisCard`'s "add a POI type" picker (filtered to searchable types not already added) and for retyping a pre-existing waypoint (full registry, no searchability filter).
- `lib/settings.ts` — persists `{device, waterSymbol}` (plus other per-type symbol overrides) to `localStorage` under key `"waypointer.settings"`, and separately persists the per-POI-type search config under key `"waypointer.poiSearch"` — kept as a sibling rather than merged in, since search config is a find-time concern and device/symbol are an export-time concern.
- shadcn/ui components live in `components/ui/` (generated source, not an npm package) — add more via `npx shadcn@latest add <name>` from `frontend/`, not by hand-writing them.
- `lib/analytics.ts` (constants factored out into `lib/analyticsConfig.ts`) wraps Umami Cloud's `window.umami.track(event, properties)` global behind a typed `track()` that no-ops (never throws) if the script never loaded — unset `VITE_UMAMI_WEBSITE_ID`, an ad-blocker, or a self-hosted deployment that opts out — so callers never need to guard for its absence. The script is injected imperatively from `main.tsx`'s `initAnalytics()` rather than a static `<script>` tag in `index.html` like Tally's, specifically so an unset website id means *zero* network calls to Umami (unlike Tally, which has no meaningful "off" state to guard). `VITE_UMAMI_WEBSITE_ID` follows the exact same non-secret build-arg pattern as `VITE_WAHOO_CLIENT_ID` (Dockerfile/docker-compose.yml) — leaving it unset is the supported way to ship the RPi/LAN deployment with no analytics at all. Individual POI/waypoint checkbox toggles are deliberately **not** tracked — exploratory clicking on a route with many candidates could burn through Umami's free-tier 100k events/month for little analytical value — only aggregate counts at `find_pois_run`/`route_saved`/`route_sent_to_wahoo` checkpoints (`selected_candidate_count`, `present_poi_types`), which is enough to derive selection behavior without per-click noise.
- `FeedbackWidget.tsx` + `lib/feedbackConfig.ts` — a Tally.so feedback form button, gated by `VITE_TALLY_FORM_ID`. Unlike Umami's env var, an unset form id has no explicit off-switch guard in the widget itself — it renders regardless, it simply has nothing to open.
