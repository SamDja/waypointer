# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Waypointer (branded "Sulla Via" in the frontend UI — `frontend/index.html`'s `<title>` and `App.tsx`'s header — but the repo, Python package (`pyproject.toml`'s `name = "waypointer"`), and all module paths keep the original name; this was a branding-only rename) is a web app: a visitor uploads a GPX route, the backend finds OpenStreetMap points of interest near it in a self-hosted PostGIS database (one query per requested POI type — see "POI types" below — at a user-configurable per-type max distance; see "PostGIS POI database" below for how that database is built), the visitor reviews/selects them on a map + checklist, and downloads a new route file with the selected POIs added — either as GPX waypoints (generic devices) or as a FIT course file (Wahoo ELEMNT ROAM v3, so each POI's icon renders correctly while navigating; see `fit_io.py` below for why this needs a whole separate code path). The visitor can also plan a route from scratch on the map, or extend/trim an imported one, road-snapped via BRouter (see `routing.py` and `lib/routePlanner.ts` below). A visitor can also connect a Wahoo account (OAuth) to push a route straight to their Wahoo app, or import a route they already have there.

Two halves in one repo, one Docker image:
- **Backend**: `src/waypointer/` — stateless FastAPI app (Python, managed with `uv`).
- **Frontend**: `frontend/` — React + TypeScript SPA (Vite, shadcn/ui, MapLibre GL via react-map-gl), built to static assets that the backend serves.

## Commands

### Backend
```bash
uv sync                                          # install deps
uv run pytest                                    # run all tests
uv run pytest tests/test_fit_io.py                # run one test file
uv run pytest tests/test_fit_io.py::test_build_course_fit_bytes_round_trip   # run one test
POSTGIS_URL=postgresql://waypointer:waypointer@localhost:5432/pois \
  uv run uvicorn waypointer.main:app --reload    # dev server at :8000
```
`uv run pytest` needs no PostGIS setup of its own for most of the suite (`test_api.py` monkeypatches `poi_db.py`'s query functions) — only `tests/test_poi_db.py` needs Docker (it spins up its own throwaway `imresamu/postgis` container via `testcontainers` and skips cleanly if Docker isn't available; not `postgis/postgis`, which is amd64-only — see "PostGIS POI database" below). The dev server above is different: every real `/api/find-pois/*` request needs `POSTGIS_URL` pointing at a running, populated instance, or it 502s (`poi_db.PoiDbError`) — see "PostGIS POI database" below for how to bring one up locally with `docker compose up -d postgis` + a small-extract `poi-import` run.

### Frontend
```bash
cd frontend
npm install
npm run dev       # Vite dev server at :5173, proxies /api/* to localhost:8000 (see vite.config.ts)
npm run build     # tsc -b && vite build -> frontend/dist/
npm test          # vitest run (lib/routePlanner.test.ts)
npm run lint       # oxlint
```
Run the backend (`uv run uvicorn ... --reload`) and `npm run dev` side by side for frontend work — the Vite proxy forwards API calls, so no CORS setup is needed. `uv run uvicorn` alone (no Vite) only serves the frontend correctly if `frontend/dist/` already exists from a prior `npm run build`; otherwise the catch-all mount in `main.py` is skipped entirely (see below) and only `/api/*` routes work.

### Docker (production shape)
```bash
docker build -t waypointer .
docker run -p 8000:8000 waypointer
```
Multi-stage: a `node` stage runs `npm ci && npm run build`, then the `python:3.11-slim` + `uv` stage copies that build output in. The only production deployment target is a Raspberry Pi 5 on the LAN, run via `docker-compose.yml` (below) — there is no cloud/PaaS deployment.

For local (LAN) use, `docker-compose.yml` wraps the same image build — `docker compose up --build -d` (reads a `.env` file in the repo root for the vars below automatically).

#### Remote access & TLS (Raspberry Pi)
The Pi is reached from outside the LAN via a [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/) (`cloudflared`, run separately from this repo — not one of the containers in `docker-compose.yml`), which forwards a public hostname to the app's published port. Cloudflare terminates TLS at its edge and proxies plain HTTP to the container, so `SSL_KEYFILE`/`SSL_CERTFILE` are unset in normal operation and `docker-compose.yml` publishes the app on host port `${PORT:-8000}` — no reverse proxy or cert management needed on the Pi itself for the tunnel path.

`uvicorn` can still terminate TLS directly when `SSL_KEYFILE`/`SSL_CERTFILE` are set — this is an opt-in fallback for browsing the app directly over the LAN without going through the tunnel (e.g. straight to the Pi's mDNS hostname), not the primary access path. Generate a self-signed cert once on the host if you want this (SAN must match how you'll browse to it):
```bash
openssl req -x509 -nodes -newkey rsa:2048 \
  -keyout waypointer.key -out waypointer.crt -days 825 \
  -subj "/CN=sampi.local" \
  -addext "subjectAltName=DNS:sampi.local"
```
Set the cert env vars via a `.env` file next to `docker-compose.yml` (never bake a private key into the image):
```bash
# .env
SSL_KEYFILE=/certs/waypointer.key
SSL_CERTFILE=/certs/waypointer.crt
CERTS_DIR=/home/pi/waypointer-certs   # host dir holding the cert/key generated above
```
then `docker compose up --build -d`. Each browser/device will show a one-time self-signed-cert trust warning on first visit over this LAN-direct path.

Whichever origin a visitor actually uses — the Cloudflare tunnel's public hostname (the normal case) or the LAN-direct address above — needs `<origin>/wahoo-callback.html` added to the registered redirect URIs in the Wahoo developer dashboard: the redirect URI is derived from `window.location.origin` (`frontend/src/lib/wahooAuth.ts`), and Wahoo requires an exact string match, so a registered URI missing the actual port (or carrying one that isn't actually there) fails with a misleading error (see [[project_wahoo_oauth_redirect_uri]]).

### Telemetry (Prometheus + Grafana + node_exporter)
Three extra `docker-compose.yml` services, LAN-only, no auth beyond Grafana's own login — the app itself has no login either, relying on Cloudflare's edge (or the Pi's LAN, for anyone with physical/network access) rather than in-app auth; see "Remote access & TLS" above. Not part of the Docker image itself — `waypointer` stays a single-responsibility container; telemetry is bolted on at the compose layer so `docker run waypointer` (no compose) still works standalone.

- **App metrics**: `prometheus-fastapi-instrumentator` is wired into `main.py` right after `app = FastAPI(...)`, exposing `GET /metrics` (request counts, latency histograms, in-progress gauge, all labeled by method/path/status). Single uvicorn process — the default in-memory `prometheus_client` registry is fine, no multiprocess mode needed (same reasoning as `rate_limit.py`'s in-process design).
- **Host metrics**: `node-exporter` mounts `/proc`, `/sys`, `/` read-only (remapped under `/host/*` with matching `--path.*` flags, the standard node_exporter compose convention) plus `pid: host`, to report real host-level CPU/mem/disk/temp rather than the container's own cgroup — temperature comes from the `hwmon`/`thermal` collectors automatically off the mounted `/sys`, no extra flag needed on modern Raspberry Pi OS kernels. Not published on a host port — only reachable from `prometheus` over the internal `waypointer-net` network.
- **Scrape config**: `monitoring/prometheus.yml` (bind-mounted read-only into the `prometheus` container) lists two jobs — `waypointer` (`waypointer:8000/metrics`) and `node` (`node-exporter:9100/metrics`) — by compose service name, not `localhost`, since Prometheus runs in its own container on the same bridge network. The normal case is plain HTTP (TLS handled externally by the Cloudflare Tunnel — see "Remote access & TLS" above), which is what this file defaults to. If you instead enable `uvicorn`'s own TLS via `SSL_KEYFILE`/`SSL_CERTFILE` for LAN-direct access, the `waypointer` job's `scheme` must be changed by hand to `https` (keeping `insecure_skip_verify: true` for the self-signed cert) — this isn't automatic, since Prometheus's static config can't react to another service's env vars.
- **Persistence**: `prometheus` and `grafana` use named Docker volumes (`prometheus-data`, `grafana-data`), not host bind-mounts — simpler to manage on the Pi, survives `docker compose down` (not `down -v`). Prometheus keeps its default 15-day retention — no tuning needed for a single-Pi personal deployment.
- **Grafana datasource**: auto-provisioned via `monitoring/grafana/provisioning/datasources/prometheus.yml` (Grafana's declarative provisioning mechanism), pointing at `http://prometheus:9090` — so Grafana has its Prometheus datasource wired up with zero manual UI clicking on first boot. Dashboards themselves are not auto-provisioned — build/import panels manually (e.g. the community node_exporter full dashboard, id `1860`, plus a hand-built panel over the `http_request_duration_seconds` histogram for app latency).
- **Access**: Grafana at `http://<pi-host>:${GRAFANA_PORT:-3000}` (default login `admin`/`${GRAFANA_ADMIN_PASSWORD:-admin}` — change the password via the Pi's `.env` file, since this is the only credential gate anywhere in this stack), Prometheus's own UI at `http://<pi-host>:${PROMETHEUS_PORT:-9090}` (useful for checking scrape target health under Status > Targets before debugging in Grafana).

### PostGIS POI database
Waypointer doesn't query the public Overpass API live. An earlier attempt to self-host a full Overpass instance (`wiktorn/overpass-api`) was tried and shelved — the vendor image's import pipeline requires bzip2-compressed OSM XML, which Geofabrik no longer publishes for country extracts, and even after fixing that, importing a whole region took 2h+ on the dev machine because the remaining import steps are inherently single-threaded (that work is preserved, unmerged, on the `infra/overpass` branch). Instead, `postgis/import_pois.lua` pre-imports only the OSM nodes/ways/relations matching `poi_types.py`'s searchable tag filters (~30 types, not a whole region) into a `pois` table via `osm2pgsql`'s flex output, and `poi_db.py` queries that table directly — no HTTP, no shared/rate-limited third party, no live fallback.

- **The `postgis` service itself is built from `postgis/db.Dockerfile`**, not pulled from `postgis/postgis` — that image publishes amd64 only, no arm64 build for any tag, which is a hard failure (`exec format error`) on the Raspberry Pi. `db.Dockerfile` is `postgres:16-bookworm` (a genuinely multi-arch Docker Official Image) with `postgresql-16-postgis-3` apt-installed on top — the same thing `postgis/postgis`'s own upstream source does, minus the missing arm64 CI target — plus an `initdb/01-postgis.sql` that runs `CREATE EXTENSION postgis` once against a fresh data directory. Only plain PostGIS is installed, not `postgis_topology`/`postgis_tiger_geocoder`/`address_standardizer`, which the upstream image bundles by default but this app never uses. Since `postgis` isn't profile-gated, `docker compose build` (no args) already builds it like any other service — no extra step needed, unlike `poi-import` below.
- **Import pipeline**: the `poi-import` `docker-compose.yml` service (built from `postgis/Dockerfile` — a small `osm2pgsql` + `postgresql-client` + `curl` image, kept separate from the main `waypointer` image since it needs neither at runtime) downloads the configured `OSM_EXTRACT_URL` (a Geofabrik regional `.osm.pbf` — no usable default, must be set in `.env` before first bring-up), drops and rebuilds the `pois` table from scratch via `osm2pgsql --output=flex --style=import_pois.lua --extra-attributes`, then adds a GIST index on `geom` and a btree index on `poi_type`. It's a one-shot job, not a long-running service — gated behind the `import` compose profile so a plain `docker compose up` doesn't try to run it — invoked via `docker compose run --rm poi-import`, directly or via `update_check.sh` below.
- **`import_pois.lua`'s `FILTERS` table** hand-mirrors `poi_types.py`'s `tag_filter` strings in Lua (same "keep two implementations in sync by hand" tradeoff this repo already accepts for `frontend/src/lib/poiTypes.ts`) — each entry names which OSM element kinds it applies to (`scope`: `"any"` mirrors an Overpass `nwr[...]` filter, `"node"`/`"way"` a narrower one) and its AND'd tag conditions (`value` for an exact match, `in_` for a regex-alternation equivalent like `shop~"^(supermarket|convenience|grocery)$"`, `exists` for a bare-key match like `shop`). Nodes import as `ST_Point`, ways as `ST_LineString` (via `as_linestring()` — works for both open and closed ways, and a closed way's vertices are all `poi_db.py`'s queries need, so true polygon semantics aren't required), and only `multipolygon`/`boundary`-type relations import (via `as_multipolygon()`) since other relation types (bus routes, turn restrictions) aren't meaningful POI locations.
- **`poi_db.py`** is the query layer: `query_pois_near_route` (`ST_DWithin` + `ST_DumpPoints` against a `LINESTRING` built from the request's route coords — the PostGIS equivalent of Overpass's `around` operator, run against the **full-resolution** route directly, no radius-padding workaround needed since there's no remote-query-size reason to simplify first, unlike the old Overpass-based query) and `query_poi_near_point` (`ST_DWithin` + `ST_ClosestPoint`, ordered by the `<->` KNN operator, for `/api/find-pois/location`'s single-point basemap-icon lookup). No TTL cache like the old `osm.py` had — repeat queries just hit local Postgres, which is fast enough on its own that an extra cache isn't worth it. `POSTGIS_URL` (a `postgresql://` DSN) is required — `poi_db.PoiDbError` is raised clearly if it's unset, no public-mirror fallback.
- **Threshold-gated reimports**: `postgis/update_check.sh`, run via a Pi-side cron entry (not baked into any container), e.g. `0 3 * * * cd /path/to/waypointer && ./postgis/update_check.sh >> postgis/state/update_check.log 2>&1`, compares the current `OSM_EXTRACT_URL` extract's size (via a HEAD request) against the size recorded at the last import (`postgis/state/.last_import_state`, gitignored, written by `import.sh` after a successful run). It only triggers a reimport (`docker compose run --rm poi-import`) once both `OSM_UPDATE_MIN_DAYS` (default 7) has elapsed *and* the size delta exceeds `OSM_UPDATE_SIZE_PCT` (default 2%) — the same deliberately coarse "how much changed" proxy the shelved Overpass attempt used, since there's no cheap way to know the real diff size without downloading and diffing the whole extract. `import.sh` itself has no idempotency check of its own — it always unconditionally drops and rebuilds `pois` — so redeploying the app must never call `docker compose run --rm poi-import` directly (that bypasses the gate every time); only first bring-up or a deliberate forced reimport should invoke it directly, everything else should go through this cron-scheduled script.
- **Sizing**: filtering at import time to only `poi_types.py`'s ~30 searchable types (instead of importing a whole Overpass-style regional dataset) is what makes this approach practical where the full-Overpass attempt wasn't — the `pois` table only ever holds rows for tags Waypointer actually searches for.
- **Local dev setup**: `docker compose up -d postgis` brings up just the database (`ports: - "${POSTGIS_PORT:-5432}:5432"` publishes it to `localhost:5432` specifically so a backend run outside Docker, e.g. `uv run uvicorn`, can reach it — the Pi's own deployment doesn't need this, since there `waypointer` and `postgis` both run in compose on the same `waypointer-net`). Then set `OSM_EXTRACT_URL` in `.env` to a **small** Geofabrik extract (a city/sub-region, e.g. Geofabrik's Île-de-France or a similarly small area — not a whole country) so the import finishes in well under a minute, and run `docker compose run --rm poi-import` once. See the "Commands" section above for the exact `POSTGIS_URL` a locally-run `uv run uvicorn`/`uv run pytest tests/test_poi_db.py` needs to point at that instance.

## Backend architecture (`src/waypointer/`)
Six endpoints, all stateless — no DB session, no server-side memory between requests (only the shared, read-only `pois` table backs POI lookups — see "PostGIS POI database" above — plus `routing.py`'s in-process leg cache). The frontend holds all state client-side and resubmits the original GPX file on every request.

- `main.py` — `POST /api/find-pois/route`, `POST /api/find-pois/location`, `POST /api/save`, `POST /api/wahoo/route-payload`, `POST /api/wahoo/import-route`, `POST /api/route-leg`. Also mounts the built SPA (`frontend/dist/`, `StaticFiles(html=True)`) at `/` as a catch-all — **this mount must stay the last thing registered in the file**, after every API route decorator, or it shadows `/api/*` entirely (Starlette matches routes in registration order). The mount is skipped if `frontend/dist/` doesn't exist, so backend-only dev without a frontend build doesn't crash on startup.
  - `find_pois` (`/api/find-pois/route`) and `find_poi_at_location` (`/api/find-pois/location`) are the same underlying PostGIS lookup at two different geometry scopes — a route polyline returning many candidates, vs a single point returning one result — hence the shared `/api/find-pois/*` prefix. `find_pois` builds the list of requested types up front (still 400s on an unknown/non-searchable `poi_type` before any PostGIS query fires), then fires them all **concurrently** via `asyncio.gather` over `asyncio.to_thread(query_pois_near_route, ...)` wrappers, each catching `poi_db.PoiDbError` independently. One type failing doesn't take the others down: it returns 200 with partial `candidates` plus a `failed_poi_types: list[FailedPoiType]`, and only 502s if *every* requested type failed. The frontend actually calls this once per POI type anyway (see frontend section), so per-request concurrency mostly matters when a caller batches several types into one `poi_config`.
  - `find_pois` also takes an optional `search_range` form field (`{start_index, end_index}` into the submitted route's coordinate list). It narrows **only** which slice of the route is handed to `query_pois_near_route`; `build_polyline_index` still runs against the *full* route, so every `distance_m`/`distance_from_start_m` is measured against the whole thing and `is_duplicate_candidate` still sees the whole file. That split is the point — the route planner re-searches just a newly appended stretch without a second place in the codebase computing distances. `route_coords` in the response must likewise always describe the whole route (simplified from `coords`, never from the slice), or a ranged re-search visibly truncates the map's route line.
  - `find_poi_at_location` resolves a click on one of the basemap's own POI icons (which carry no OSM id/tags) to the real OSM element within `LOOKUP_POI_RADIUS_M` (40m), returning a `PoiLookupResult`. Takes no `gpx_file` — it must work before any route is loaded.
  - `save` and `wahoo_route_payload` share `_build_fit_course_points`, which merges newly-selected candidates with kept (non-discarded) pre-existing waypoints into one FIT course-point list — each kept waypoint's type comes from the `existing_waypoint_types` form field (JSON dict, original-index-as-string → poi_type key, from the visitor correcting `infer_poi_type`'s guess), defaulting to `"generic"`. In `save`'s GPX branch, `_resolve_symbol` (visitor's `symbols` override → the type's `default_gpx_symbol` → its `label`) is applied to kept waypoints *before* `discard_waypoints` runs — ordering matters because `discard_waypoints`/`existing_waypoint_types` both index against the upload's *original* (pre-discard) waypoint order.
  - `wahoo_route_payload` builds the same FIT bytes as `save`'s FIT branch (always FIT, regardless of the visitor's local-download device choice — Wahoo's route push has no GPX equivalent) plus distance/ascent/name metadata for the browser to POST to Wahoo's `/v1/routes`, computed server-side since only the backend ever has the full-resolution, elevation-carrying route (`/api/find-pois/route` only ships the frontend a simplified, elevation-stripped polyline).
  - `wahoo_import_route` downloads a Wahoo-hosted FIT route server-side (Wahoo's CDN has no CORS headers, so the browser can't fetch it directly) and converts it to GPX via `fit_read.py`, so an imported route re-enters the same GPX-only pipeline as a manual upload. SSRF guard: the caller-supplied `file_url`'s host must equal or suffix-match `WAHOO_FILE_HOST_SUFFIX = ".wahooligan.com"`. No Wahoo access token is sent — the CDN URL is expected to already be publicly fetchable.
  - `route_leg_endpoint` (`/api/route-leg`) road-snaps one leg between two route-planner anchors via `routing.py`, offloaded with `asyncio.to_thread`; a bad profile or invalid `options` (a JSON-object form field, parsed with a `dict[str, Any]` `TypeAdapter` so values arrive as sent and `resolve_options` does the kind checks) is a 400, a `RoutingError` a 502. Proxied rather than called from the browser so the provider stays swappable server-side, the leg cache is shared across visitors, and the per-IP routing budget actually protects the shared BRouter instance.
- `poi_types.py` — the POI type registry (`POI_TYPES`, not a plugin system, mirrors `device_profiles.py`'s style): ~55 entries today. Most are **not searchable** (`tag_filter=None` — used only to classify pre-existing waypoints via `infer_poi_type` and to pick a FIT icon via `course_point_type`); a `tag_filter` plus `min_distance_m`/`max_distance_m`/`default_max_distance_m` bounds (enforced by `clamp_distance_m`) makes a type searchable — imported into the PostGIS `pois` table (see `postgis/import_pois.lua`, which mirrors these same `tag_filter`s in Lua). Only `water` sets `default_gpx_symbol` (`"Water"`) — every other type falls back to its `label` for the GPX `<sym>` tag. `DEFAULT_VISIBLE_POI_TYPES = ("water",)` is what a fresh browser sees pre-populated (water is the core use case; a visitor adds more via the frontend's "add a POI type" picker) and is also `find_pois`'s fallback when the `poi_config` form field is omitted entirely. `POI_TYPE_BY_COURSE_POINT_TYPE` is the reverse mapping (course_point_type → key), built as a plain dict comprehension because uniqueness is asserted by `test_poi_types.py` against `dev_tools/wahoo_poi_mapping.json`; `fit_read.py` uses it to recover a POI's type from a FIT file without guessing from text. This is the single source of truth for POI types — `frontend/src/lib/poiTypes.ts` mirrors it by hand, same convention as `schemas.py`/`candidate.ts` below.
- `geometry.py` — pure-stdlib haversine/point-to-segment/point-to-polyline distance, and `simplify_rdp` (Ramer-Douglas-Peucker). `simplify_rdp`'s output is used **only** for the map's route line now — `main.py`'s PostGIS query runs against the full-resolution, unsimplified route (or its `search_range` slice) directly (no radius-padding workaround needed, unlike the old Overpass-based query, since a local DB query has no query-size reason to run against a simplified route). The authoritative "is this POI within range" check in `main.py` still runs against the full-resolution route too, using each request's own per-type clamped distance (not a single global constant) — mostly a safety net now, since PostGIS' own `ST_DWithin` already restricted results to that radius server-side.
- `poi_db.py` — the PostGIS query layer that replaced Overpass entirely; see "PostGIS POI database" above for the full picture (`query_pois_near_route`, `query_poi_near_point`, the `OsmNode` dataclass, `POSTGIS_URL`/`PoiDbError`).
- `routing.py` — BRouter client for the in-app route planner (`/api/route-leg`), shaped as an "external HTTP dependency with a cache": env-overridable `ROUTING_URL` (defaults to BRouter's public instance — no API key), a `TTLCache`, a descriptive `USER_AGENT` (also reused by `main.py`'s Wahoo download), one error type the endpoint maps to a 502. BRouter was chosen over managed alternatives because its cycling profiles explicitly weight *against traffic* rather than merely preferring cycling infrastructure, and because its GeoJSON carries elevation inline as a 3rd coordinate — which matters, since a FIT course with no altitude renders flat black on a ROAM. Two gotchas: BRouter's `lonlats` is lon,lat while everything here is `(lat, lon)`; and it answers some failures with a plain-text body under a 200, so a non-JSON body is an error, not a parse bug. The caller-supplied profile is checked against `ALLOWED_PROFILES` rather than forwarded. Per-profile BRouter options (`PROFILE_OPTIONS`: `BoolOption`/`ChoiceOption` with defaults — hand-mirrored by `frontend/src/lib/mapStyles.ts`'s `routingOptions`) are validated by `resolve_options`, which rejects unknown keys and wrong kinds (a bool where a number is expected and vice versa, or a number outside the offered choices) with `ValueError` → 400, fills every missing option with its default, and encodes them BRouter's way — booleans as `1`/`0` (BRouter answers `true` with an empty body), numbers as plain decimals — sent as `profile:<name>=<value>` query parameters. Every exposed option is always sent explicitly and is part of the cache key, so the key is unambiguous and a change of defaults on the public instance can't quietly change a route. Ferries and steps default *off*, unlike `fastbike-lowtraffic`'s own defaults.
- `ttl_cache.py` — the generic in-process TTL cache used by `routing.py` (reset between tests by `tests/conftest.py`).
- `gpx_io.py` — GPX parsing/merging via `gpxpy`, operating on bytes only (no filesystem I/O anywhere in the request path). Dedup of previously-added POIs works by stamping a custom `<extensions><waypointer:osm_id>` marker on GPX waypoints and checking for it on re-upload, with a proximity fallback for waypoints that lack the marker (hand-edited files, other tools) — this dedup is POI-type-agnostic, keyed only on OSM id/location. `discard_waypoints(gpx, indices)` removes pre-existing `<wpt>` entries by their position in the *original* upload's waypoint list (see `ExistingWaypoint.index` in `schemas.py`) — it must run before `add_waypoints` appends any newly selected candidates, since indices are only meaningful against the pre-discard order. `infer_poi_type(wpt)` best-effort classifies a pre-existing waypoint, in priority order: (1) a stamped `poi_type` extension marker (written by `stamp_poi_type`, used when the waypoint came from `fit_read.py`) wins outright; (2) else a stamped `osm_id` marker (a waypoint we ourselves previously added) → `"water"` (safe today since water is still the only auto-added type — revisit if that changes); (3) else substring-match the waypoint's `<sym>`/`<type>` text against each registered type's `sym_hints`; (4) else `"generic"`. Deliberately never matches against `<name>` — free-text names cause false positives (e.g. "Water Street Cafe").
- `fit_io.py` — builds a full ridable FIT course (not just isolated waypoints) using the `fit-tool` library. **A POI's icon on a Wahoo does not come from the standard FIT `course_point.type` enum** — reverse-engineering a real Komoot→Wahoo-generated FIT file (see `dev_tools/`) showed the icon is driven by a custom developer field named `course_point_type` (uint8), keyed per POI type in `poi_types.py` (e.g. `16` = water). This was later confirmed against the device for the full 0-99 range (`dev_tools/wahoo_poi_mapping.json`). The native `type` field is left as `CoursePoint.GENERIC` to match the confirmed-working reference file.
- `fit_read.py` — the inverse of `fit_io.py`: parses an existing FIT file (`fit_tool.FitFile.from_bytes`) into GPX bytes, used by `/api/wahoo/import-route`. `RecordMessage`s become one `GPXTrack`/`GPXTrackSegment`; `CoursePointMessage`s become `GPXWaypoint`s, each stamped with its recovered POI type (via the same developer field `fit_io.py` writes, looked up in `POI_TYPE_BY_COURSE_POINT_TYPE`, `"generic"` if absent/unrecognized) so `infer_poi_type` doesn't need to guess on next upload. fit-tool's position getters already return degrees, no semicircle conversion needed. Raises `ValueError` if the file has no positioned track points — a FIT with course points but no track isn't a usable route, and `main.py` surfaces that as a 400.
- `device_profiles.py` — small registry (`DEVICE_PROFILES`, not a plugin system) mapping a device key to just `{name, output_format}` (`GPX` or `FIT`) — two entries, `generic` and `wahoo_elemnt_roam_v3`. The format-specific values this used to hold directly (GPX symbol, FIT course_point_type) have moved into `poi_types.py`'s per-type registry now that POI types number in the dozens, not just water.
- `rate_limit.py` — in-memory per-IP sliding window, built by `make_rate_limit(bucket, budget, window)` and keyed on `(bucket, ip)` so each endpoint gets its own budget (all per `WINDOW_S = 60.0`): `/api/find-pois/route` (`REQUESTS_PER_WINDOW = 60`), `/api/find-pois/location` (`LOOKUP_POI_REQUESTS_PER_WINDOW = 30`), and `/api/route-leg` (`ROUTING_REQUESTS_PER_WINDOW = 60` — route planning is inherently chatty, since dragging an anchor re-requests its two adjacent legs, and sharing one budget would let a planning session starve the search it feeds). The find-pois budget is sized generously because the frontend fans one "Find POIs" click into one `/api/find-pois/route` call *per selected POI type* (see frontend section) rather than one combined call — this endpoint gets hit N times instead of once for the same amount of work, so the budget covers a full-registry search (~30 searchable types) plus a couple of re-searches within the window. The POI buckets just guard this app's own DB/CPU usage now that lookups hit local PostGIS; the routing bucket still protects a shared third party (BRouter's public instance). Single-process only, not meant to survive multiple workers/restarts.
- `schemas.py` — the Pydantic response/request shapes shared with the frontend's TS types: `Candidate` (carries `poi_type`), `PoiSearchConfig` (one entry per requested POI type + its max distance, sent as a JSON-string form field to `/api/find-pois/route`, same pattern as `/api/save`'s `selected_candidates`), `SearchRange` (an inclusive index range into the submitted route, narrowing **only** the PostGIS query — see `find_pois` above), `PoiLookupResult` (`/api/find-pois/location`'s response, carrying the element's full raw tag dict — kept separate from `Candidate`, which round-trips through `/api/save`), `ExistingWaypoint` (a pre-existing `<wpt>` from the uploaded file, tagged with its `index` in that file's original waypoint list and a best-effort inferred `poi_type` — editable client-side before it affects export), `FailedPoiType` (one requested type whose PostGIS query errored, `find_pois` returns a list of these instead of failing the whole request), `FindPoisResponse`, `RouteLegResponse` (one routed leg: index-parallel `coords`/`elevations` plus `distance_m`), and `WahooRoutePayload` (FIT bytes as base64 + display metadata for a browser-side POST to Wahoo)
  (`frontend/src/types/candidate.ts` mirrors these by hand — keep them in sync manually when changing one side). `/api/save` and `/api/wahoo/route-payload` both accept `discarded_waypoint_indices` (JSON-string, defaults `"[]"`), `existing_waypoint_types` (JSON-string dict, defaults `"{}"`), and an optional `route_name`; `/api/save` alone also accepts `symbols` (JSON-string dict, poi_type → GPX `<sym>` override, defaults `"{}"`). `route_name` is kept separate from the sanitized output filename stem (`_safe_filename_stem` vs `_display_name` in `main.py`) so a user-typed name isn't mangled for filesystem safety before being shown as FIT `course_name`/Wahoo `route[name]`.

`dev_tools/` is exploratory tooling, not part of the shipped app: `generate_test_waypoints.py` builds a FIT file with all 100 `course_point_type` values laid out in a grid for manual on-device icon testing; `wahoo_poi_mapping.json` and `POIs.csv` are the resulting reverse-engineered value→icon mapping (cross-referenced against Strava/RideWithGPS/komoot's own POI category names) — this is the source of truth `poi_types.py`'s `course_point_type` values and `test_poi_types.py`'s assertions are checked against.

## Frontend architecture (`frontend/src/`)

- `App.tsx` owns all cross-cutting state via plain `useState` (no Redux/Context — intentionally, the tree is shallow). `selectedIds: Set<number>` is shared between `RouteMap` (map marker popups) and `CandidateChecklist` (the list) — both are just different views over the same state and call the same `onToggle`, which is what keeps map-popup and checklist selection in sync with no extra glue code. `keptWaypointIndices: Set<number>` is the equivalent for pre-existing waypoints from the uploaded file — defaults to "all kept" on every successful search, and `SaveCard` inverts it (kept → discarded) into the indices it sends to `/api/save`. `waypointTypeOverrides: Record<number, string>` holds the visitor's corrections to `infer_poi_type`'s guess for pre-existing waypoints (indexed by original waypoint index, applied on top of `existingWaypoints` via `useMemo`, survives a later re-search) — wired into both `ImportCard`'s "Waypoints" tab and `RouteMap` via `onChangeWaypointType`; there is no separate "assign waypoint types" dialog component, this is inline per-row editing via `PoiTypeCombobox`. `searchedPoiTypes` snapshots which POI types + distances were actually searched for at find-time, so `CandidateChecklist`'s per-type subsections (and their empty states) don't shift if the visitor tweaks step 2's inputs after results are already showing, without re-running the search. `clickAddedCandidates`/`clickAddedDetails` hold POIs added by clicking a basemap icon (via `/api/find-pois/location`), kept as siblings to `findResult` so a click works before any search or route exists; `allCandidates` merges the two. Other cross-cutting state: `wahooTokens` (loaded from `lib/wahooSettings.ts`/localStorage), `mapStyleKey`, `hoveredPoi` (shared hover highlight between map and checklist, `{kind: "candidate" | "waypoint", id}`), `openStep` (accordion-style step-card open/closed state).
  - `handleFind` (the "Find POIs" button) is just `runFind(file, undefined)`. `runFind(targetFile, searchRange?)` fires one `findPois(file, [entry], searchRange)` call **per POI-type entry**, not one call carrying every type — staggered by `SEARCH_STAGGER_MS` (200ms) × index, smallest `max_distance_m` first, via `Promise.allSettled` (they still overlap in flight, just not at the same instant; the staggering predates the move off the public Overpass mirror to a local PostGIS DB and is kept mainly so results still stream in progressively per type, per `FindPoisCard`'s per-row status). Without a range, each type that's unchanged since the last search and didn't previously fail is skipped (`isAlreadySatisfied`, compared against `searchedPoiTypes`), surfacing an "already up to date" toast if nothing needed re-fetching. Results accumulate into a plain mutable object (not React state) pushed into `setFindResult` after each chunk resolves, so the map and checklist fill in progressively per type instead of waiting for the slowest one; a previously-failed or previously-missing type's completion/error status drives `FindPoisCard`'s per-row spinner/check/warning icon and its running `(done+errored/total)` count in the button label.
  - With a `searchRange` (the route planner's debounced re-search after an extend — `scheduleReSearch`, `RE_SEARCH_DEBOUNCE_MS`), `runFind` reuses `searchedPoiTypes` as its config rather than step 2's current inputs, never skips a type (the route changed), carries over **every** existing candidate, and merges each chunk in (a re-found `(osm_id, poi_type)` replaces the old one, since its distances were measured against the edited route). The range is resolved when the timer *fires*, not when scheduled: an appended leg starts as a straight-line placeholder and is replaced by routed geometry moments later, and only the untouched prefix is stable across that swap. Trims never re-search — the route only shrinks.
  - **Route planner state**: `plannerState` is non-null exactly while planning, and is then the source of truth for the route's geometry — one effect synthesizes `file` from it (`lib/gpx.ts`'s `buildGpxFile`, re-serializing from the imported `sourceDoc` so pre-existing `<wpt>` entries and their `waypointer:` markers survive), which is what keeps `/api/find-pois/route`, `/api/save` and the Wahoo push unaware the planner exists. A second effect fetches any leg still missing routed geometry (`pendingLegs`), de-duplicated via an in-flight ref and deliberately never cancelled (a leg is keyed on its own endpoints, so a late response is always either still wanted or a harmless no-op). An edit that would strand a checked waypoint/candidate further than `offRouteThresholdM` from the route is held in `pendingEdit` and confirmed via `OffRouteDialog`, which unchecks the stranded items on confirm (`trackedPositions` holds each tracked item's incremental distance — see `routePlanner.ts`). Every committed edit pushes the *previous* `PlannerState` onto `plannerPast` (capped at `PLANNER_HISTORY_LIMIT`), along with the keys that edit unchecked; `stepPlannerHistory` pops one entry, merges the current leg cache into it (so stepping back never re-fetches geometry), re-checks those keys, and unchecks whatever the restored route now strands — with a toast rather than `OffRouteDialog`, since the visitor asked for exactly that route back — recording them on the opposite stack so stepping back again re-checks them. Tracked positions are recomputed (`seedTracked`) rather than stored, which also covers candidates found since. Routed geometry arriving later (`withLeg`) is not a history step. Undo/redo, the selected point (`selectedAnchorIndex`, set by clicking any planner point including the green/red ends, which opens `RouteMap`'s `SelectedPointPopup` on it with the delete action (the popup is the only selection indicator — no ring on the marker) — deletion lives on the map, not in `PlannerPanel`; while a point is selected, a click elsewhere on the map only dismisses it rather than also appending a point) and any `pendingEdit` all reset per planning session (`resetPlannerSession`). Shortcuts (Ctrl/⌘+Z, Ctrl/⌘+Shift+Z or Ctrl+Y, Delete/Backspace on the selected point, Escape to deselect) are a window listener bound once per session via a ref, ignored inside inputs and dialogs. Edits without their own notion of what changed (deleting a point, undo/redo) use `commonPrefixLength` to re-search POIs only past the unchanged prefix, and not at all when the route merely shrank. Deleting points can take a route below two points, in which case the synthesizing effect clears `file`; "Done" with no route left behaves like "Remove route".
- `RouteMap.tsx` always renders (a MapLibre `Map` via `react-map-gl/maplibre`, with a neutral default view before any route is loaded) — the map is meant to be persistently visible, not conditionally mounted. Before `/api/find-pois/route` returns, it shows a route line parsed client-side (`lib/gpx.ts`, via the browser's `DOMParser`, no library) purely for instant visual feedback on import; once the backend responds, it switches to the backend's authoritative `route_coords` + candidate markers. POI candidates render as `Marker`s wrapping `lib/mapIcons.tsx`'s `CircleMarkerIcon` — the candidate's `poi_type` is looked up in `POI_TYPES` to pick its icon and color, with opacity distinguishing selected/unselected. Every coordinate in this codebase is `[lat, lon]`; `toLngLat` flips at the MapLibre boundary and nowhere else. Marker `onClick`s must call `e.originalEvent.stopPropagation()` or the click reaches the map's own handler in the same tick (which closes the popup that was just opened, and — while planning — would also drop an anchor). The route's start/end points get their own non-interactive `Marker`+`Tooltip` via `RouteEndpointMarkers` — green start, red end, collapsed into one marker when they coincide (loop routes). `RouteDirectionArrows` overlays arrowheads via a `symbol` layer with `symbol-placement: line`, re-registering its icon on every `styledata` event since swapping styles wipes custom images. Imperative map work is done in small `useMap()`-based child components (`FitBounds`, `BearingSync`, `PlanningCursor`, `BasemapPoiFilter`) with cleanup in the effect's return. The basemap's own POI icons (`BASEMAP_POI_LAYER_IDS`, filtered by `BasemapPoiFilter`/`lib/basemapPoiMapping.ts` to addable types) are made clickable via `interactiveLayerIds`; a click resolves the feature's own point geometry (not the click position, which may be on the label) through `onBasemapPoiClick` → `/api/find-pois/location`. Map cartography is switchable via `lib/mapStyles.ts`'s `MAP_STYLES` registry — today just one real style, `road_cycling` (a hand-forked OpenFreeMap "liberty" style at `frontend/public/map-styles/road-cycling.json` that highlights dedicated cycleways and grays out bike-prohibited/unpaved roads), plus commented-out placeholders for other activity types with no custom cartography yet; each style also names the BRouter profile the planner uses (`routingProfileForStyle`) and an `icon`. The picker for it is `MapStyleSelect.tsx`, which sits at the top of the sidebar above the step cards/`PlannerPanel` rather than on the map, since the choice sets the whole session's activity (cartography + routing), not just the map's look. `MapLegend.tsx` + `lib/mapStyleLegend.ts` derive the legend's colors/labels by evaluating the *actual* style JSON's paint expressions at render time rather than hand-copying colors, so the legend can't drift from the style file.

  **Planning mode** activates when the optional `planning` prop is present. Clicking empty map appends a point; clicking the route itself does nothing. Basemap POI icons are **not** clickable while planning (`interactiveLayerIds` is cleared), so a click always means "add a point". Interior points render as draggable numbered circles (the anchor index *is* the number, so they read 1, 2, 3 in ride order), while the route's ends are the green/red `RouteEndpointMarkers` themselves made draggable — deliberately no anchor dot or trim handle stacked on top of them, and a loop route stops collapsing its two coincident ends into one marker so both stay grabbable. Dragging the route line inserts a point: an invisible 16px-wide copy of the line (`route-line-hit`) exists purely as a pointer target, since the visible 3px line can't be grabbed reliably. `isOnRouteLine` is a **screen-space** hit test against that layer, used both to suppress the click-to-append and to decide whether an endpoint was dropped "on the route" — a distance-in-metres threshold would be ~2px wide zoomed out and enormous zoomed in. `FitBounds` is disabled while planning: `routeCoords` changes on every edit, and refitting each time yanks the viewport out from under the visitor. `map.dragPan` must be reached through `useMap().getMap()` — it's a handler object, not a method, so react-map-gl's `MapRef` doesn't proxy it.
- Layout is a full-page map with the header and a right sidebar (`md:w-1/3 md:min-w-[480px]`, not a fixed pixel width) floating over it. Both are transparent and `pointer-events-none` so clicks in their empty space reach the map; only their contents (the header's logo and Wahoo pills, the sidebar's cards) are opaque and `pointer-events-auto`. `lib/useMapInsets.ts` measures how much of the map they cover and `RouteMap`'s `insets` prop keeps its top overlay controls (via `--map-inset-top`) and fit-to-route padding clear of them. The `<Map>` element is its own stacking context (`isolation: isolate`): markers and popups all live inside it and carry z-indices up to 1500, which would otherwise render above the floating header/sidebar (`z-20`) — map elements, POIs included, must always stay below the surrounding UI. That would trap MapLibre's corner controls too, so the attribution is MapLibre's own `AttributionControl` mounted by `DetachedAttribution` into a host element *outside* the `<Map>` (`attributionControl={false}` on the map itself); index.css pins that host to the page's bottom-right corner, directly below `FeedbackWidget`'s button and on the same vertical centre line. It keeps MapLibre's show-then-collapse-on-first-drag behaviour, which OSM's attribution guidelines require. Below `md` the sidebar stacks under a `50vh` map instead (only the header floats). All of `RouteMap`'s own controls (pan, zoom, compass, center-on-route, locate) are grouped bottom-left, since anything on the right would hang mid-map beside the sidebar; everything floating over the map carries a shadow (`shadow-lg` for pills/cards, `shadow-md` for map buttons) because the cards' background is too close in tone to the basemap on its own. The sidebar holds collapsible, numbered `StepCard`s (✅-suffixed once complete), in order: `ImportCard` (empty state offers two equal choices — "Load a route" (drag-and-drop/click-to-browse, Wahoo import) or "Plan a new route"; once a route is loaded, an "Edit route" button opens the planner on it; also a "Waypoints" tab for reviewing/retyping the upload's pre-existing `<wpt>` entries) → `FindPoisCard` (one row per POI type the visitor has added — every listed type is always searched, there's no per-row enable checkbox anymore; types are added via `PoiTypeCombobox`'s "add a POI type" picker and removed via a per-row remove button; columns are grid-aligned regardless of label width) → `CandidateChecklist` (only once results exist; renders one subsection per searched POI type — with its own empty state if that type found nothing — plus, if the uploaded file already had any `<wpt>` entries, an "Already in this file" subsection with a keep/discard checkbox and retype control per one; shared row rendering lives in `PoiListItem.tsx`) → `SaveCard` (device/format selection, route naming via `RouteNameDialog.tsx`, save, and a "send to Wahoo" action, only once results exist). While `plannerState` is non-null the step cards are replaced entirely by `PlannerPanel.tsx` — planning and the find/save flow are separate phases, so they don't share the sidebar; its "Done" (`handleExitPlanning`) hands back to the step cards with step 2 open if a route exists. `RouteStats.tsx` (distance/duration/elevation + the avg-speed input) and `RemoveRouteButton.tsx` (the confirmed "Remove route" action) are shared by `ImportCard` and `PlannerPanel`. `PlannerPanel` also holds `PlannerPointList.tsx`: one row per planner point in ride order (badge matching its map marker, distance from the previous point — `~` while that leg is still routing — and a delete ✕), reorderable by dragging a row's handle or by keyboard, via `@dnd-kit` (`core` + `sortable` + `modifiers`). Hovering a row and hovering a marker share `hoveredAnchorIndex` in `App.tsx`, so each highlights the other (markers glow via `CircleMarkerIcon`'s `highlighted` prop).
- **Wahoo integration** (`lib/wahooConfig.ts`, `wahooAuth.ts`, `wahooConnect.ts`, `wahooApi.ts`, `wahooSettings.ts`, `components/WahooProfileMenu.tsx`, `WahooRoutesDialog.tsx`) — PKCE OAuth2 public-client flow (no client secret) against Wahoo's API, requesting `user_read routes_read routes_write` scopes (`routes_read` isn't used by anything today, requested pre-emptively for future use; `missingWahooScopeWarning()` checks granted-vs-requested since Wahoo can silently under-grant). `connectWahoo()` opens a popup rather than a full-page redirect, specifically to avoid losing in-progress upload state held in `App.tsx`'s `useState`; it listens for a `postMessage` from `wahoo-callback.html` (present at `frontend/public/wahoo-callback.html`, copied into the build), which is where the `<origin>/wahoo-callback.html` redirect-URI requirement described above comes from. Connect success/failure is observed from `connectWahoo()`'s own promise resolution back in the original tab, not from the callback page itself (which isn't part of the SPA and isn't instrumented). `WahooRoutesDialog` is one shared component driven by a `mode: "import" | "manage"` prop: full-screen listing of the visitor's Wahoo routes, with rename (`RouteNameDialog.tsx`, also reused for pre-save naming) and delete (confirmed via the shadcn `AlertDialog`) in "manage" mode, one-click import in "import" mode — import round-trips through the backend's `/api/wahoo/import-route`.
- `lib/api.ts` — thin typed `fetch` wrappers, one function per backend endpoint, no abstraction beyond that.
- `lib/routePlanner.ts` — the route planner's model and edit operations; pure, no React or MapLibre, and the one part of the frontend with unit tests (`routePlanner.test.ts`, vitest, `npm test`). A route is an ordered list of **segments**, each either `fixed` (imported geometry, verbatim) or `routed` (a BRouter leg, geometry held in a cache keyed on `(from, to, profile)`). That makes drawing from scratch and editing an import the same feature: import → one `fixed` segment, trim → slice it (zero routing calls), extend → append/prepend a `routed` leg. `insertAnchorAt` splits the segment under a point; splitting a `fixed` segment yields two `fixed` halves whose concatenated geometry is **byte-identical** to before, which is what makes an imported route safe to start editing — only *moving* the new point re-routes, and only the two stretches either side of it (`moveAnchor` converts an adjacent `fixed` segment to `routed`). `removeAnchor` is the inverse: deleting an interior point merges its two segments — two `fixed` neighbours rejoin byte-identically (undoing an `insertAnchorAt` split with no routing), otherwise the merged stretch becomes one `routed` leg between the neighbours' own far ends (their `from`/`to`, not `plannerAnchors`' snapped points, so other legs keep matching their cache keys); deleting an end drops its segment, and is refused next to `fixed` geometry for the same whole-import reason as `moveAnchor`. `reorderAnchors` (the point-list drag) keeps, by identity, every segment whose two anchors stay consecutive in the same direction and makes every new pair a `routed` leg; it refuses any reorder that would break up a `fixed` segment (imported stretches keep their order), since on a pristine import that would replace the whole track. `plannerLegDistancesM` gives each segment's length for the list.

  **Dead-end spur removal**: a point dropped slightly off the road the route should follow (a few metres up a side street) makes BRouter route in to it and straight back out. BRouter's own `correctMisplacedViaPoints` can't help — it only fixes via points *inside* one request, and the planner routes one leg per request — so `segmentGeometries` does it on assembly: where routed leg *i*'s end and leg *i+1*'s start retrace the same road (`spurPointCount`, matching points within `SPUR_MATCH_M`, never cutting a leg below two points), and that stretch is no longer than the point's `spurToleranceM`, both are cut back to where they diverge — so the point's marker then sits there too. The tolerance is stored on the routed segment ending at that point, set by `appendAnchor`/`moveAnchor` from `spurToleranceM(zoom, latitude)` (`SPUR_TOLERANCE_PX` = 30px on the ground at the zoom the point was placed at; `RouteMap`'s `onZoomChange` feeds `App.tsx`'s `mapZoomRef`), so a point placed zoomed out is forgiven a large spur and one placed zoomed in is kept as deliberate. Split and merge carry the tolerance of the point a segment still ends at. It never applies next to `fixed` geometry, isn't part of the leg cache key, and never modifies the cached legs; every consumer of segment geometry (`outboundGeometry`, `plannerAnchors`, `plannerLegDistancesM`, `insertAnchorAt`) goes through `segmentGeometries`, so distances measured on the drawn route and the model's segment lengths agree. A loop's return leg isn't spur-checked.

  **Routing options** live on `PlannerState.options` and are part of every leg's cache key (`legKey(from, to, profile, options)`), so changing one (`setRoutingOptions`, `App.tsx`'s `handleRoutingOptionsChange` — one undoable edit, also saved as the style's preference) makes every routed leg pending and re-fetched, while `fixed` geometry is untouched and switching back or undoing is free from cache. While a leg is being re-routed, `segmentGeometry` draws the geometry it had under other options (`previouslyRoutedLeg`) rather than a straight line, so the route doesn't collapse and the off-route check doesn't measure against placeholders; only legs with no geometry at all (`unroutedLegs`) are dashed. The fetch effect passes the options a request was made with to `withLeg`'s `routedWith`, so a response arriving after the options changed is cached under its own key, not the current one. `RoutingOptionsSection.tsx` is the collapsible "Routing preferences" UI (choice → `Select`, toggle → `Checkbox`, header counts options changed from default).

  **Route shape** (`RouteShape`: `one-way` / `loop` / `out-and-back`, a field on `PlannerState`, switched via `setRouteShape` — which needs ≥2 points — and PlannerPanel's segmented toggle) says what comes after the last point. The return part is **derived, never stored**: `outboundGeometry` is the route as drawn, and `plannerGeometry` appends a loop's `returnLeg` (a virtual routed leg from the last anchor back to the start, fetched like any other since `pendingLegs` includes it; skipped when the ends are already within `ANCHOR_SNAP_M`) or an out-and-back's reversed outbound geometry (no routing). Anchors stay the outbound points only, which is why appending, deleting, reordering and moving need no shape special-cases — a new point automatically lands before the return. Trims measure and cut `outboundGeometry`; `plannerGeometry` (whole route as ridden) is what the map draws, what's exported, and what distance caps, stats and POI searches use. `removeAnchor` drops back to one-way below two points. In `App.tsx`, any edit to a loop/out-and-back goes through `applyEditWithFullReprojection` instead of the incremental trim/extend tracking, because the derived return changes with every edit so the old route is never a prefix of the new one; a line-drag grab past the outbound part maps to "append before the return" for a loop and to the mirrored outbound position for an out-and-back. A route that finishes where it starts (a planned loop/out-and-back, or any loaded route whose ends coincide) shows one combined start/finish marker (`START_FINISH_BACKGROUND`, a green/red split with a flag) instead of separate start/end markers; while planning, the last anchor is then an ordinary numbered point.

  What an endpoint drag does keys off `endpointNeighbourKind`, not off "imported vs drawn": next to a routed leg it moves, next to `fixed` geometry it extends or trims. That distinction exists because on a pristine import `segments[0]` spans the *whole* route, so treating a start-drag as a move would replace an 80km track with one routed leg. `moveAnchor` therefore still refuses an endpoint whose neighbour is fixed, and `App.tsx`'s `handleMoveEndpoint` routes those to `prependAnchor`/`appendAnchor`/`trimStart`/`trimEnd` instead.

  The anchor/segment indexing is load-bearing and easy to get wrong: `start` is held as its own field precisely so anchor 0 is `segments[0]`'s start and anchor *i* is `segments[i-1]`'s end and `segments[i]`'s start. The incremental distance updates are **exact, not approximate** — a trim only shrinks the route so distances can only increase (only points whose nearest segment was removed need recomputing), and an extend only grows it so distances can only decrease (measure against the new legs alone and keep the smaller). The tests assert these equal a full recompute; they caught five real indexing bugs when first written.
- `lib/poiTypes.ts` — hand-mirrors the backend's `poi_types.py` registry (key, label, searchability, default/min/max search distance), plus two frontend-only display fields with no backend equivalent: `icon` (a `LucideIcon`) and `color` (the marker/popup color for that type) — mirrors the full ~55-entry registry, not just water. `PoiTypeCombobox.tsx` (a `Popover` + `cmdk` `Command` searchable combobox) exists specifically because that entry count is too many for a plain `<Select>`; it's used both for `FindPoisCard`'s "add a POI type" picker (filtered to searchable types not already added) and for retyping a pre-existing waypoint (full registry, no searchability filter).
- `lib/settings.ts` — persists `{device, waterSymbol}` (plus other per-type symbol overrides) to `localStorage` under key `"waypointer.settings"`, and separately persists the per-POI-type search config under key `"waypointer.poiSearch"` — kept as a sibling rather than merged in, since search config is a find-time concern and device/symbol are an export-time concern. Same sibling-not-merged rule for `"waypointer.mapStyle"` (display-time), `"waypointer.avgSpeedKmh"` (estimate-time), `"waypointer.offRouteThreshold"` (edit-time: how far a route edit may strand a waypoint before it is flagged for unchecking) and `"waypointer.routingOptions"` (plan-time: the BRouter options, keyed by map style since each style is an activity with its own profile; `loadRoutingOptions` drops anything saved the style no longer offers or of the wrong kind).
- shadcn/ui components live in `components/ui/` (generated source, not an npm package) — add more via `npx shadcn@latest add <name>` from `frontend/`, not by hand-writing them.
- `lib/analytics.ts` (constants factored out into `lib/analyticsConfig.ts`) wraps Umami Cloud's `window.umami.track(event, properties)` global behind a typed `track()` that no-ops (never throws) if the script never loaded — unset `VITE_UMAMI_WEBSITE_ID`, an ad-blocker, or a self-hosted deployment that opts out — so callers never need to guard for its absence. The script is injected imperatively from `main.tsx`'s `initAnalytics()` rather than a static `<script>` tag in `index.html` like Tally's, specifically so an unset website id means *zero* network calls to Umami (unlike Tally, which has no meaningful "off" state to guard). `VITE_UMAMI_WEBSITE_ID` follows the exact same non-secret build-arg pattern as `VITE_WAHOO_CLIENT_ID` (Dockerfile/docker-compose.yml) — leaving it unset is the supported way to ship the RPi/LAN deployment with no analytics at all. Individual POI/waypoint checkbox toggles are deliberately **not** tracked — exploratory clicking on a route with many candidates could burn through Umami's free-tier 100k events/month for little analytical value — only aggregate counts at `find_pois_run`/`route_saved`/`route_sent_to_wahoo` checkpoints (`selected_candidate_count`, `present_poi_types`), which is enough to derive selection behavior without per-click noise.
- `FeedbackWidget.tsx` + `lib/feedbackConfig.ts` — a Tally.so feedback form button, gated by `VITE_TALLY_FORM_ID`. Unlike Umami's env var, an unset form id has no explicit off-switch guard in the widget itself — it renders regardless, it simply has nothing to open.
