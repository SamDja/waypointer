# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Waypointer (branded "Sulla Via" in the frontend UI — `frontend/index.html`'s `<title>` and `App.tsx`'s header — but the repo, Python package (`pyproject.toml`'s `name = "waypointer"`), and all module paths keep the original name; this was a branding-only rename) is a web app: a visitor uploads a GPX route, the backend finds OpenStreetMap points of interest near it in a self-hosted PostGIS database (one query per requested POI type — see "POI types" below — at a user-configurable per-type max distance; see "PostGIS POI database" below for how that database is built), the visitor reviews/selects them on a map + checklist, and downloads a new route file with the selected POIs added — either as GPX waypoints (generic devices) or as a FIT course file (Wahoo ELEMNT ROAM v3, so each POI's icon renders correctly while navigating; see `fit_io.py` below for why this needs a whole separate code path). The visitor can also plan a route from scratch on the map, or extend/trim an imported one, road-snapped via BRouter (see `routing.py` and `lib/routePlanner.ts` below). A visitor can also connect a Wahoo account (OAuth) to push a route straight to their Wahoo app, or import a route they already have there — and a Strava account, to import its saved routes or a recorded activity's track (Strava's API can't receive routes; see `strava.py` below).

Two halves in one repo, one Docker image:
- **Backend**: `src/waypointer/` — stateless FastAPI app (Python, managed with `uv`).
- **Frontend**: `frontend/` — React + TypeScript SPA (Vite, shadcn/ui, MapLibre GL via react-map-gl), built to static assets that the backend serves.

## Commands

### Backend
```bash
uv sync                                          # install deps
uv run pytest                                    # run all tests
uv run pytest tests/test_fit_io.py                # run one test file
uv run pytest tests/test_fit_io.py::test_build_course_fit_bytes_round_trip   # run one test
POSTGIS_URL=postgresql://waypointer:waypointer@localhost:5432/pois \
DATABASE_URL=postgresql://waypointer:waypointer@localhost:5432/sulla_via \
TOKEN_ENCRYPTION_KEY=<a Fernet key, see token_crypto.py> WAHOO_CLIENT_ID=<...> \
  uv run uvicorn waypointer.main:app --reload    # dev server at :8000
```
`uv run pytest` needs no PostGIS setup of its own for most of the suite (`test_api.py` monkeypatches `poi_db.py`'s query functions) — only `tests/test_poi_db.py` needs Docker (it spins up its own throwaway `imresamu/postgis` container via `testcontainers` and skips cleanly if Docker isn't available; not `postgis/postgis`, which is amd64-only — see "PostGIS POI database" below). The dev server above is different: every real `/api/find-pois/*` request needs `POSTGIS_URL` pointing at a running, populated instance, or it 502s (`poi_db.PoiDbError`) — see "PostGIS POI database" below for how to bring one up locally with `docker compose up -d postgis` + a small-extract `poi-import` run.

cd frontend

npm run build     # tsc -b && vite build -> frontend/dist/

### Docker (production shape)
```bash
docker build -t waypointer .
docker run -p 8000:8000 waypointer
```
Multi-stage: a `node` stage runs `npm ci && npm run build`, then the `python:3.11-slim` + `uv` stage copies that build output in. The only production deployment target is a Raspberry Pi 5 on the LAN, run via `docker-compose.yml` (below) — there is no cloud/PaaS deployment.

For local (LAN) use, `docker-compose.yml` wraps the same image build — `docker compose up --build -d` (reads a `.env` file in the repo root for the vars below automatically).

#### Remote access & TLS (Raspberry Pi)
The Pi is reached from outside the LAN via a [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/) (`cloudflared`, run separately from this repo — not one of the containers in `docker-compose.yml`), which forwards a public hostname to the app's published port. Cloudflare terminates TLS at its edge and proxies plain HTTP to the container, so `SSL_KEYFILE`/`SSL_CERTFILE` are unset in normal operation and `docker-compose.yml` publishes the app on host port `${PORT:-8000}` — no reverse proxy or cert management needed on the Pi itself for the tunnel path.

`uvicorn` can still terminate TLS directly when `SSL_KEYFILE`/`SSL_CERTFILE` are set — this is an opt-in fallback for browsing the app directly over the LAN without going through the tunnel (e.g. straight to the Pi's mDNS hostname), not the primary access path. Generate a self-signed cert once on the host if you want this (SAN must match how you'll browse to it):
```bash
openssl req -x509 -nodes -newkey rsa:2048 \
  -keyout waypointer.key -out waypointer.crt -days 825 \
  -subj "/CN=sampi.local" \
  -addext "subjectAltName=DNS:sampi.local"
```
Set the cert env vars via a `.env` file next to `docker-compose.yml` (never bake a private key into the image):
```bash
# .env
SSL_KEYFILE=/certs/waypointer.key
SSL_CERTFILE=/certs/waypointer.crt
CERTS_DIR=/home/pi/waypointer-certs   # host dir holding the cert/key generated above
```
then `docker compose up --build -d`. Each browser/device will show a one-time self-signed-cert trust warning on first visit over this LAN-direct path.

Whichever origin a visitor actually uses — the Cloudflare tunnel's public hostname (the normal case) or the LAN-direct address above — needs `<origin>/wahoo-callback.html` added to the registered redirect URIs in the Wahoo developer dashboard: the redirect URI is derived from `window.location.origin` (`frontend/src/lib/wahooAuth.ts`), and Wahoo requires an exact string match, so a registered URI missing the actual port (or carrying one that isn't actually there) fails with a misleading error (see [[project_wahoo_oauth_redirect_uri]]).

#### Log retention
The privacy notice promises the app's logs are kept for 14 days (`frontend/src/privacy/privacyConfig.ts`'s `LOG_RETENTION`). The access log carries each request's path, query string included, so a search's typed text and map centre end up there. Docker's own logging drivers (`json-file`, `local`) can only rotate by size, so `docker-compose.yml` sends the `waypointer` service's logs to the host's systemd journal (`logging: driver: journald`, tagged `waypointer`), and the retention is enforced on the Pi in `/etc/systemd/journald.conf`, not in the repo:
```ini
[Journal]
Storage=persistent
MaxRetentionSec=13day
MaxFileSec=1day
SystemMaxUse=200M
```
then `sudo systemctl restart systemd-journald`. journald deletes a journal file only once everything in it has passed `MaxRetentionSec`, so one file per day (`MaxFileSec`) plus 13 days means nothing is kept past 14. `SystemMaxUse` caps disk use as a safety net. Caveats:
- The setting is for the **whole journal**, so every system service on the Pi gets the same retention.
- `Storage=volatile` (in memory) would silently lose the logs at every reboot.

To change the period, change `MaxRetentionSec` and `LOG_RETENTION` together. `docker compose logs waypointer` still reads them, and so does `journalctl CONTAINER_TAG=waypointer`. On a host without journald (a Mac running OrbStack or Docker Desktop), set `LOG_DRIVER=json-file` in `.env` (the driver is `${LOG_DRIVER:-journald}`) - the container won't start otherwise.

### Telemetry (Prometheus + Grafana + node_exporter)
Three extra `docker-compose.yml` services, LAN-only, no auth beyond Grafana's own login — the app itself has no login either, relying on Cloudflare's edge (or the Pi's LAN, for anyone with physical/network access) rather than in-app auth; see "Remote access & TLS" above. Not part of the Docker image itself — `waypointer` stays a single-responsibility container; telemetry is bolted on at the compose layer so `docker run waypointer` (no compose) still works standalone.

- **App metrics**: `prometheus-fastapi-instrumentator` is wired into `main.py` right after `app = FastAPI(...)`, exposing `GET /metrics` (request counts, latency histograms, in-progress gauge, all labeled by method/path/status). Single uvicorn process — the default in-memory `prometheus_client` registry is fine, no multiprocess mode needed (same reasoning as `rate_limit.py`'s in-process design).
- **Host metrics**: `node-exporter` mounts `/proc`, `/sys`, `/` read-only (remapped under `/host/*` with matching `--path.*` flags, the standard node_exporter compose convention) plus `pid: host`, to report real host-level CPU/mem/disk/temp rather than the container's own cgroup — temperature comes from the `hwmon`/`thermal` collectors automatically off the mounted `/sys`, no extra flag needed on modern Raspberry Pi OS kernels. Not published on a host port — only reachable from `prometheus` over the internal `waypointer-net` network.
- **Scrape config**: `monitoring/prometheus.yml` (bind-mounted read-only into the `prometheus` container) lists two jobs — `waypointer` (`waypointer:8000/metrics`) and `node` (`node-exporter:9100/metrics`) — by compose service name, not `localhost`, since Prometheus runs in its own container on the same bridge network. The normal case is plain HTTP (TLS handled externally by the Cloudflare Tunnel — see "Remote access & TLS" above), which is what this file defaults to. If you instead enable `uvicorn`'s own TLS via `SSL_KEYFILE`/`SSL_CERTFILE` for LAN-direct access, the `waypointer` job's `scheme` must be changed by hand to `https` (keeping `insecure_skip_verify: true` for the self-signed cert) — this isn't automatic, since Prometheus's static config can't react to another service's env vars.
- **Persistence**: `prometheus` and `grafana` use named Docker volumes (`prometheus-data`, `grafana-data`), not host bind-mounts — simpler to manage on the Pi, survives `docker compose down` (not `down -v`). Prometheus keeps its default 15-day retention — no tuning needed for a single-Pi personal deployment.
- **Grafana datasource**: auto-provisioned via `monitoring/grafana/provisioning/datasources/prometheus.yml` (Grafana's declarative provisioning mechanism), pointing at `http://prometheus:9090` — so Grafana has its Prometheus datasource wired up with zero manual UI clicking on first boot. Dashboards themselves are not auto-provisioned — build/import panels manually (e.g. the community node_exporter full dashboard, id `1860`, plus a hand-built panel over the `http_request_duration_seconds` histogram for app latency).
- **Access**: Grafana at `http://<pi-host>:${GRAFANA_PORT:-3000}` (default login `admin`/`${GRAFANA_ADMIN_PASSWORD:-admin}` — change the password via the Pi's `.env` file, since this is the only credential gate anywhere in this stack), Prometheus's own UI at `http://<pi-host>:${PROMETHEUS_PORT:-9090}` (useful for checking scrape target health under Status > Targets before debugging in Grafana).

### PostGIS POI database
Waypointer doesn't query the public Overpass API live. An earlier attempt to self-host a full Overpass instance (`wiktorn/overpass-api`) was tried and shelved — the vendor image's import pipeline requires bzip2-compressed OSM XML, which Geofabrik no longer publishes for country extracts, and even after fixing that, importing a whole region took 2h+ on the dev machine because the remaining import steps are inherently single-threaded (that work is preserved, unmerged, on the `infra/overpass` branch). Instead, `postgis/import_pois.lua` pre-imports only the OSM nodes/ways/relations matching `poi_types.py`'s searchable tag filters (~30 types, not a whole region) into a `pois` table via `osm2pgsql`'s flex output, and `poi_db.py` queries that table directly — no HTTP, no shared/rate-limited third party, no live fallback.

- **The `postgis` service itself is built from `postgis/db.Dockerfile`**, not pulled from `postgis/postgis` — that image publishes amd64 only, no arm64 build for any tag, which is a hard failure (`exec format error`) on the Raspberry Pi. `db.Dockerfile` is `postgres:16-bookworm` (a genuinely multi-arch Docker Official Image) with `postgresql-16-postgis-3` apt-installed on top — the same thing `postgis/postgis`'s own upstream source does, minus the missing arm64 CI target — plus an `initdb/01-postgis.sql` that runs `CREATE EXTENSION postgis` once against a fresh data directory. Only plain PostGIS is installed, not `postgis_topology`/`postgis_tiger_geocoder`/`address_standardizer`, which the upstream image bundles by default but this app never uses. Since `postgis` isn't profile-gated, `docker compose build` (no args) already builds it like any other service — no extra step needed, unlike `poi-import` below.
- **Import pipeline**: the `poi-import` `docker-compose.yml` service (built from `postgis/Dockerfile` — a small `osm2pgsql` + `postgresql-client` + `curl` image, kept separate from the main `waypointer` image since it needs neither at runtime) downloads the configured `OSM_EXTRACT_URL` (a Geofabrik regional `.osm.pbf` — no usable default, must be set in `.env` before first bring-up), cuts it down with `osmium tags-filter` against `postgis/prefilter.txt`, drops and rebuilds the `pois` table from scratch via `osm2pgsql --output=flex --style=import_pois.lua --extra-attributes`, then adds a GIST index on `geom` and a btree index on `poi_type`. The osmium step is what makes a country extract practical: osm2pgsql (1.8, bookworm) reads the file and runs the Lua callbacks on **one core** for every object in the extract, whatever `--number-processes` says (that only parallelises the final index build), and `--cache` does nothing without `--slim` — so the only lever is a smaller input. `prefilter.txt` is a deliberately coarse superset (whole keys, except `highway`/`natural`, which are narrowed to values); referenced nodes/ways are kept so way and multipolygon geometries still build, and the Lua stays the authority on what is imported. It's a one-shot job, not a long-running service — gated behind the `import` compose profile so a plain `docker compose up` doesn't try to run it — invoked via `docker compose run --rm poi-import`, directly or via `update_check.sh` below. **`import_pois.lua` and `prefilter.txt` are `COPY`d into that image, and `docker compose run` does not rebuild** — so editing a filter and re-running the import silently reimports with the *old* filters, and the new type just comes back empty with no error anywhere. Run `docker compose build poi-import` (or `docker compose run --build --rm poi-import`) after touching either file.
- **`import_pois.lua`'s `FILTERS` table** hand-mirrors `poi_types.py`'s `tag_filter` strings in Lua, but unlike `frontend/src/lib/poiTypes.ts` this mirror **is checked**: `tests/test_import_pois_lua.py` parses both sides and asserts they describe the same tags with the same scope, since the failure is otherwise silent and only shows up as "that type finds nothing" after a full reimport. It parses strictly, so a condition written in a shape the parser doesn't know fails the test rather than going unchecked — teach the test about any new form. The same test checks that `prefilter.txt` covers every `FILTERS` entry, so a filter on a new tag key must be added there too. Not every `FILTERS` entry is a POI type: `poi_types.py`'s `INTERNAL_IMPORT_FILTERS` lists rows imported for the backend's own use — today `mountain_pass` (`node["mountain_pass"="yes"]`, the route generator's known climbs) — with no registry entry (`POI_TYPES` must match Wahoo's icon mapping one-for-one), no frontend mirror and no Find-POIs picker; the test checks them like any searchable type. Each entry names which OSM element kinds it applies to (`scope`: `"any"` mirrors an Overpass `nwr[...]` filter, `"node"`/`"way"` a narrower one) and its AND'd tag conditions (`value` for an exact match, `in_` for a regex-alternation equivalent like `shop~"^(supermarket|convenience|grocery)$"`, `exists` for a bare-key match like `shop`). Nodes import as `ST_Point`, ways as `ST_LineString` (via `as_linestring()` — works for both open and closed ways, and a closed way's vertices are all `poi_db.py`'s queries need, so true polygon semantics aren't required), and only `multipolygon`/`boundary`-type relations import (via `as_multipolygon()`) since other relation types (bus routes, turn restrictions) aren't meaningful POI locations.
- **`poi_db.py`** is the query layer: `query_pois_near_route` (`ST_DWithin` + `ST_DumpPoints` against a `LINESTRING` built from the request's route coords — the PostGIS equivalent of Overpass's `around` operator, run against the **full-resolution** route directly, no radius-padding workaround needed since there's no remote-query-size reason to simplify first, unlike the old Overpass-based query) and `query_poi_near_point` (`ST_DWithin` + `ST_ClosestPoint`, ordered by the `<->` KNN operator, for `/api/find-pois/location`'s single-point basemap-icon lookup). No TTL cache like the old `osm.py` had — repeat queries just hit local Postgres, which is fast enough on its own that an extra cache isn't worth it. `POSTGIS_URL` (a `postgresql://` DSN) is required — `poi_db.PoiDbError` is raised clearly if it's unset, no public-mirror fallback.
- **Threshold-gated reimports**: `postgis/update_check.sh`, run via a Pi-side cron entry (not baked into any container), e.g. `0 3 * * * cd /path/to/waypointer && ./postgis/update_check.sh >> postgis/state/update_check.log 2>&1`, compares the current `OSM_EXTRACT_URL` extract's size (via a HEAD request) against the size recorded at the last import (`postgis/state/.last_import_state`, gitignored, written by `import.sh` after a successful run). It only triggers a reimport (`docker compose run --rm poi-import`) once both `OSM_UPDATE_MIN_DAYS` (default 7) has elapsed *and* the size delta exceeds `OSM_UPDATE_SIZE_PCT` (default 2%) — the same deliberately coarse "how much changed" proxy the shelved Overpass attempt used, since there's no cheap way to know the real diff size without downloading and diffing the whole extract. `import.sh` itself has no idempotency check of its own — it always unconditionally drops and rebuilds `pois` — so redeploying the app must never call `docker compose run --rm poi-import` directly (that bypasses the gate every time); only first bring-up or a deliberate forced reimport should invoke it directly, everything else should go through this cron-scheduled script.
- **Sizing**: filtering at import time to only `poi_types.py`'s ~30 searchable types (instead of importing a whole Overpass-style regional dataset) is what makes this approach practical where the full-Overpass attempt wasn't — the `pois` table only ever holds rows for tags Waypointer actually searches for.
- **Local dev setup**: `docker compose up -d postgis` brings up just the database (`ports: - "${POSTGIS_PORT:-5432}:5432"` publishes it to `localhost:5432` specifically so a backend run outside Docker, e.g. `uv run uvicorn`, can reach it — the Pi's own deployment doesn't need this, since there `waypointer` and `postgis` both run in compose on the same `waypointer-net`). Then set `OSM_EXTRACT_URL` in `.env` to a **small** Geofabrik extract (a city/sub-region, e.g. Geofabrik's Île-de-France or a similarly small area — not a whole country) so the import finishes in well under a minute, and run `docker compose run --rm poi-import` once — preceded by `docker compose build poi-import` whenever `import_pois.lua`/`prefilter.txt` changed, per the rebuild note above. See the "Commands" section above for the exact `POSTGIS_URL` a locally-run `uv run uvicorn`/`uv run pytest tests/test_poi_db.py` needs to point at that instance.

## Backend architecture (`src/waypointer/`)
The route/POI endpoints are all stateless — no server-side memory between requests (only the shared, read-only `pois` table backs POI lookups — see "PostGIS POI database" above — plus `routing.py`'s in-process leg cache, `geocode.py`'s search cache and `photos.py`'s photo cache). The frontend holds all route state client-side and resubmits the original GPX file on every request. The one exception is **optional user accounts** (`/api/auth/*`, `/api/account/*` — see "Accounts" below), which keep users and sessions in their own database; nothing about routes or POIs is stored there.

- `main.py` — `POST /api/find-pois/route`, `POST /api/find-pois/location`, `GET /api/map-pois`, `POST /api/save`, the Wahoo calls made with the account's stored connection — `POST /api/wahoo/routes` (push), `GET /api/wahoo/routes`, `POST /api/wahoo/routes/{id}/rename`, `POST /api/wahoo/routes/{id}/delete` — and `POST /api/wahoo/import-route`, `POST /api/route-leg`, `GET /api/geocode`, `POST /api/poi-photos`, and the Strava calls, likewise made with the stored connection — `GET /api/strava/routes`, `POST /api/strava/import-route`, `GET /api/strava/activities`, `POST /api/strava/import-activity` (see `strava.py`). Connecting and disconnecting apps (`/api/{strava,wahoo}/authorize-url`, `/api/{strava,wahoo}/connect`, `/api/connections*`) live in `connections.py`'s router, and the account endpoints in `auth.py`'s — both included just before the SPA mount. Also mounts the built SPA (`frontend/dist/`, `StaticFiles(html=True)`) at `/` as a catch-all — **this mount must stay the last thing registered in the file**, after every API route decorator, or it shadows `/api/*` entirely (Starlette matches routes in registration order). The mount is skipped if `frontend/dist/` doesn't exist, so backend-only dev without a frontend build doesn't crash on startup.
  - `find_pois` (`/api/find-pois/route`) and `find_poi_at_location` (`/api/find-pois/location`) are the same underlying PostGIS lookup at two different geometry scopes — a route polyline returning many candidates, vs a single point returning one result — hence the shared `/api/find-pois/*` prefix. `find_pois` builds the list of requested types up front (still 400s on an unknown/non-searchable `poi_type` before any PostGIS query fires), then fires them all **concurrently** via `asyncio.gather` over `asyncio.to_thread(query_pois_near_route, ...)` wrappers, each catching `poi_db.PoiDbError` independently. One type failing doesn't take the others down: it returns 200 with partial `candidates` plus a `failed_poi_types: list[FailedPoiType]`, and only 502s if *every* requested type failed. The frontend actually calls this once per POI type anyway (see frontend section), so per-request concurrency mostly matters when a caller batches several types into one `poi_config`.
  - `find_pois` also takes an optional `search_range` form field (`{start_index, end_index}` into the submitted route's coordinate list). It narrows **only** which slice of the route is handed to `query_pois_near_route`; `build_polyline_index` still runs against the *full* route, so every `distance_m`/`distance_from_start_m` is measured against the whole thing and `is_duplicate_candidate` still sees the whole file. That split is the point — the route planner re-searches just a newly appended stretch without a second place in the codebase computing distances. `route_coords` in the response must likewise always describe the whole route (simplified from `coords`, never from the slice), or a ranged re-search visibly truncates the map's route line.
  - `map_pois` (`GET /api/map-pois`) answers "what of ours is in view", for drawing our own imported POIs on the map. It exists because the basemap cannot show some of them at all: OpenMapTiles' POI mapping has no `tourism=wilderness_hut`, so an unstaffed bivouac never reaches the tiles however the style is written, while our import does hold it. Distinct from `/api/find-pois/*`, which answers "what's near this route" and returns distances; there's no route here to measure against. `MAP_POI_TAG_MATCHES` narrows each requested registry type to what's actually worth drawing — a registry type is built for searching and is deliberately coarse (`lodging` is anything you can sleep in), and this overlay only earns its keep for what the tiles omit, so staffed alpine huts are deliberately **not** in it: they already come from the basemap, everywhere, while our own POIs exist only inside the configured extract's region. Refuses a viewport wider than `MAP_POI_MAX_SPAN_DEG` (1°) rather than asking PostGIS for a continent, and caps rows at `MAP_POI_LIMIT`.
  - `find_poi_at_location` resolves a click on one of the basemap's own POI icons (which carry no OSM id/tags) to the real OSM element within `LOOKUP_POI_RADIUS_M` (40m), returning a `PoiLookupResult`. Takes no `gpx_file` — it must work before any route is loaded.
  - `save` and `wahoo_push_route` both run their parsed selection through `_dedupe_by_specificity` first (one waypoint per `osm_id`, keeping the most specific `poi_type`) — the frontend already resolves this for searched candidates, so this is the net that catches a click-added collision, and two course points on one coordinate are just noise on the device. They then share `_build_fit_course_points`, which merges newly-selected candidates with kept (non-discarded) pre-existing waypoints into one FIT course-point list — each kept waypoint's type comes from the `existing_waypoint_types` form field (JSON dict, original-index-as-string → poi_type key, from the visitor correcting `infer_poi_type`'s guess), defaulting to `"generic"`. In `save`'s GPX branch, `_resolve_symbol` (visitor's `symbols` override → the type's `default_gpx_symbol` → its `label`) is applied to kept waypoints *before* `discard_waypoints` runs — ordering matters because `discard_waypoints`/`existing_waypoint_types` both index against the upload's *original* (pre-discard) waypoint order.
  - `wahoo_push_route` (`POST /api/wahoo/routes`, verified account) builds the same FIT bytes as `save`'s FIT branch (`_wahoo_route_upload`; always FIT, regardless of the visitor's local-download device choice — Wahoo's route push has no GPX equivalent) plus distance/ascent/name metadata, computed server-side since only the backend ever has the full-resolution, elevation-carrying route (`/api/find-pois/route` only ships the frontend a simplified, elevation-stripped polyline), and pushes it to Wahoo itself with the account's token (`wahoo.push_route`). Each push creates a new Wahoo route (fresh `external_id`).
  - `wahoo_import_route` downloads a Wahoo-hosted FIT route server-side (Wahoo's CDN has no CORS headers, so the browser can't fetch it directly) and converts it to GPX via `fit_read.py`, so an imported route re-enters the same GPX-only pipeline as a manual upload. SSRF guard: the caller-supplied `file_url`'s host must equal or suffix-match `WAHOO_FILE_HOST_SUFFIX = ".wahooligan.com"`. No Wahoo access token is sent (and no account needed) — the CDN URL is expected to already be publicly fetchable.
  - `route_leg_endpoint` (`/api/route-leg`) road-snaps one leg between two route-planner anchors via `routing.py`, offloaded with `asyncio.to_thread`; a bad profile or invalid `options` (a JSON-object form field, parsed with a `dict[str, Any]` `TypeAdapter` so values arrive as sent and `resolve_options` does the kind checks) is a 400, a `RoutingError` a 502. Proxied rather than called from the browser so the provider stays swappable server-side, the leg cache is shared across visitors, and the per-IP routing budget actually protects the shared BRouter instance.
- `poi_types.py` — the POI type registry (`POI_TYPES`, not a plugin system, mirrors `device_profiles.py`'s style): ~55 entries today. Most are **not searchable** (`tag_filter=None` — used only to classify pre-existing waypoints via `infer_poi_type` and to pick a FIT icon via `course_point_type`); a `tag_filter` plus `min_distance_m`/`max_distance_m`/`default_max_distance_m` bounds (enforced by `clamp_distance_m`) makes a type searchable — imported into the PostGIS `pois` table. `specificity` (default 0) settles the case where **one element honestly matches several searched types at once**: `nwr["shop"]` structurally contains every `shop=*` type, and a node can be `highway=trailhead` *and* `tourism=information` (an info board at a trail start, e.g. OSM node 6337835209), so the import deliberately writes one row per matching type and the higher `specificity` wins at display/export time — `shopping` is `-1`, `trailhead` is `1`, everything else 0. It's only ever compared between types the visitor actually searched, so searching the broader type alone still finds the element. (Searchable types are imported into the PostGIS `pois` table by `postgis/import_pois.lua`, which mirrors these same `tag_filter`s in Lua.) Only `water` sets `default_gpx_symbol` (`"Water"`) — every other type falls back to its `label` for the GPX `<sym>` tag. `DEFAULT_VISIBLE_POI_TYPES = ("water",)` is what a fresh browser sees pre-populated (water is the core use case; a visitor adds more via the frontend's "add a POI type" picker) and is also `find_pois`'s fallback when the `poi_config` form field is omitted entirely. `POI_TYPE_BY_COURSE_POINT_TYPE` is the reverse mapping (course_point_type → key), built as a plain dict comprehension because uniqueness is asserted by `test_poi_types.py` against `dev_tools/wahoo_poi_mapping.json`; `fit_read.py` uses it to recover a POI's type from a FIT file without guessing from text. This is the single source of truth for POI types — `frontend/src/lib/poiTypes.ts` mirrors it by hand, same convention as `schemas.py`/`candidate.ts` below.
- `geometry.py` — pure-stdlib haversine/point-to-segment/point-to-polyline distance, and `simplify_rdp` (Ramer-Douglas-Peucker). `simplify_rdp`'s output is used **only** for the map's route line now — `main.py`'s PostGIS query runs against the full-resolution, unsimplified route (or its `search_range` slice) directly (no radius-padding workaround needed, unlike the old Overpass-based query, since a local DB query has no query-size reason to run against a simplified route). The authoritative "is this POI within range" check in `main.py` still runs against the full-resolution route too, using each request's own per-type clamped distance (not a single global constant) — mostly a safety net now, since PostGIS' own `ST_DWithin` already restricted results to that radius server-side.
- `poi_db.py` — the PostGIS query layer that replaced Overpass entirely; see "PostGIS POI database" above for the full picture (`query_pois_near_route`, `query_poi_near_point` and its nearest-N form `query_pois_near_point`, `query_pois_in_bounds`, the `OsmNode` dataclass, `POSTGIS_URL`/`PoiDbError`).
- `routing.py` — BRouter client for the in-app route planner (`/api/route-leg`), shaped as an "external HTTP dependency with a cache": env-overridable `ROUTING_URL` (defaults to BRouter's public instance — no API key), a `TTLCache`, a descriptive `USER_AGENT` (also reused by `main.py`'s Wahoo download), one error type the endpoint maps to a 502. BRouter was chosen over managed alternatives because its cycling profiles explicitly weight *against traffic* rather than merely preferring cycling infrastructure, and because its GeoJSON carries elevation inline as a 3rd coordinate — which matters, since a FIT course with no altitude renders flat black on a ROAM. `route_leg` is a two-point wrapper over `route_via(points, …, alternative)`, which routes any number of points in one request and can ask for one of BRouter's alternatives (`alternativeidx` 0–`MAX_ALTERNATIVE`) — the route generator's way of keeping to one call per candidate. Two gotchas: BRouter's `lonlats` is lon,lat while everything here is `(lat, lon)`; and it answers some failures with a plain-text body under a 200, so a non-JSON body is an error, not a parse bug. The caller-supplied profile is checked against `ALLOWED_PROFILES` rather than forwarded. Each leg also carries its **surface**: `_parse_surface` reads BRouter's GeoJSON `messages` table (a header row, then one row per stretch with its own `Distance` and space-separated `WayTags`) into ordered `SurfaceRun`s (consecutive same-category stretches merged; their distances sum to the leg's) plus `cycleway_m` (`highway=cycleway`). `surface_category` maps tags to paved / cobbles / unpaved / unknown — an explicit `surface` wins; untagged major roads (`MAJOR_ROADS`) count as paved and tracks go by `tracktype`, anything else untagged is honestly unknown; cobbles are their own category because they matter to a road bike. The table is informational, so anything malformed yields no surface data rather than failing the leg. Per-profile BRouter options (`PROFILE_OPTIONS`: `BoolOption`/`ChoiceOption` with defaults — hand-mirrored by `frontend/src/lib/mapStyles.ts`'s `routingOptions`) are validated by `resolve_options`, which rejects unknown keys and wrong kinds (a bool where a number is expected and vice versa, or a number outside the offered choices) with `ValueError` → 400, fills every missing option with its default, and encodes them BRouter's way — booleans as `1`/`0` (BRouter answers `true` with an empty body), numbers as plain decimals — sent as `profile:<name>=<value>` query parameters. Every exposed option is always sent explicitly and is part of the cache key, so the key is unambiguous and a change of defaults on the public instance can't quietly change a route. An option name BRouter doesn't recognise is *silently ignored* (200, unmodified route) rather than refused, so this allowlist is the only thing catching a misspelled one. Two profiles are allowed today. For cycling, `fastbike` rather than `fastbike-lowtraffic`: the two are identical except for `consider_traffic`'s default (0.1 vs 1), and since that option is always sent explicitly, the choice of profile only sets the default answer to the traffic question ("A little"); ferries and steps default *off* there, unlike `fastbike`'s own defaults. For hiking, `hiking-mountain` rather than the `hiking-beta` the public instance also still serves — `hiking-beta` was dropped from BRouter upstream after v1.6.3 (so self-hosting would lose it) and declares no `# %name%` options at all, while `hiking-mountain` is in upstream master and declares each option with its type and range. Its options are the SAC-scale preference, the marked-trail preference, mud avoidance and climbing avoidance, and there steps and ferries keep the profile's own defaults (*on*) — both are ordinary parts of a walking route. Its hard `SAC_scale_limit` cap is deliberately not exposed alongside the soft `SAC_scale_preferred`, since two SAC knobs read as one setting contradicting the other.
- `geocode.py` — place search for the map's search box (`GET /api/geocode?q=&lat=&lon=`), built the same way as `routing.py`: env-overridable `GEOCODE_URL` (defaults to Photon, komoot's public OSM geocoder — no API key, and unlike Nominatim its usage policy allows search-as-you-type), a `TTLCache`, the shared `USER_AGENT`, and `GeocodeError` → 502 (a query outside 3–200 characters is a `ValueError` → 400). Results are restricted by repeated `osm_tag` include filters (`place`, `natural`, `mountain_pass`, OR'd by Photon) so a village search doesn't also return its bus stops and shops; the `lat`/`lon` bias (the map's centre) is rounded to 1 decimal so small pans still hit the cache. Photon's `extent` is `[west, north, east, south]` — `_place` reorders it to `[west, south, east, north]` for `PlaceResult.bbox`. Names come back in the local language ("Italia", not "Italy").
- `photos.py` — the photos an OSM element's tags point to, for its map popup (`POST /api/poi-photos`, form field `tags` = the element's photo tags as a JSON object). Built like `geocode.py` (fixed service URLs, a `TTLCache` capped at an hour because Mapillary's signed thumbnail URLs expire, the shared `USER_AGENT`). `photo_refs` reads `image`, `wikimedia_commons` (`File:` or `Category:`), `panoramax` (UUID), `mapillary` (numeric id) and `wikidata` (P18, followed only when nothing else points at Commons), each also numbered (`panoramax:1`) and `;`-separated, dropping any value not shaped as its key promises. **SSRF guard: nothing found in the tags is ever fetched** — only Commons, Wikidata, Panoramax's federated meta-catalogue (`api.panoramax.xyz`, which resolves an id whatever instance holds it) and Mapillary's Graph API are called, with checked ids; an `image` URL that isn't on Commons is handed to the browser as-is (an https image file is shown, anything else linked). `resolve_photos` resolves each service independently — one failing is named in `failed_sources` rather than hiding the others, and the endpoint only 502s when there was nothing but failures — keeps only Commons files whose `mediatype` is `BITMAP` (categories also hold audio, video, PDFs and DjVu scans — which come with a rendered page as a thumbnail, so they'd pass for a photo — and SVG coats of arms/logos; a category asks for `CATEGORY_MEMBERS_FETCHED` members so dropping those still leaves up to `MAX_CATEGORY_FILES`), de-duplicates by full URL, and sorts newest first (Commons' `DateTimeOriginal`, falling back to the upload time; Panoramax's capture `datetime`; Mapillary's `captured_at`), undated last. Author and licence come along because Commons' CC-BY-SA requires the credit. `MAPILLARY_TOKEN` (optional, runtime env, server-side only) enables Mapillary; without it a Mapillary id becomes a link (`links`) instead of an error. Rate-limited per IP by its own bucket (`PHOTO_REQUESTS_PER_WINDOW = 60`, one request per popup opened).
- `strava.py` — the Strava API client. Strava's token exchange needs the app's `client_secret` and Strava has no PKCE, so it has always been server-side; every Strava call goes through here, so the rate limit, error mapping and credentials sit in one place and nothing depends on Strava's CORS. The tokens are stored with the visitor's account and refreshed by `connections.py` (see "Accounts"); the browser never holds one, and the athlete id the route list needs comes from the stored connection, never from the request. `get_athlete` (`GET /athlete`) is how an imported browser-held connection learns whose it is. `STRAVA_CLIENT_ID`/`STRAVA_CLIENT_SECRET` are runtime env, read per call — unset, the endpoints answer 503 (`StravaNotConfiguredError`) and the frontend says Strava isn't set up; the frontend never sees the client id (the backend builds the authorize URL, and only for `<origin>/strava-callback.html`). Scope is `read,read_all,activity:read_all` — `read_all` because most planned routes are private, and `activity:read_all` rather than `activity:read` because the latter cuts privacy-zone stretches (usually the ends) out of a track, which is no longer a route you can follow. A refused code/token (Strava answers a bad code with 400) maps to 401 so the frontend's reconnect message fires; a Strava 429 is passed on with `Retry-After` like BRouter's. Route ids are read from **`id_str`** — they overflow a JS number. `export_route_gpx` only accepts an all-digit id (the SSRF guard: nothing caller-shaped reaches the URL), and `/api/strava/import-route` checks the export parses with a track before handing it back as-is — Strava already exports GPX, so no conversion. **Activities** are the other import source: `list_activities` returns **one page** (`ACTIVITIES_PER_PAGE` = 20, `/api/strava/activities?page=N` → `StravaActivitiesPage {activities, has_more}`) of those with a GPS track (skipping trainer, manual and position-less ones) — an athlete can have thousands, so the dialog fetches the next page only on "Load more activities"; `has_more` is judged on what Strava sent before that filtering, so a page of indoor rides doesn't end the list early, and since Strava's API has no GPX export for activities, `export_activity_gpx` builds one from the activity's `latlng` + `altitude` streams (`key_by_type=true`; altitude kept where recorded, since a FIT course without elevation renders flat on a ROAM). An activity with no GPS stream is a visitor-facing 400. **Strava's API has no route write endpoints at all** (no create, rename or delete; `/uploads` takes activities, which would land in the visitor's feed), so Strava is import-only here, and the save card only tells a Strava-connected visitor how to import the GPX by hand. Two operational limits outside the code: a new Strava API app accepts only one connected athlete until Strava reviews it, and the callback domain registered on it must match the origin visitors use.
- `route_request.py` + `llm.py` — the first step of generating routes from plain words (served by `nl_routes.py`, below): **the LLM parses, it doesn't route.** `ParsedRequest` is exactly what the model fills — every field required and nullable, no defaults or numeric bounds, `$ref`s inlined by `parsed_schema()`, because that's what strict structured-output modes accept across providers; numbers are checked afterwards (`check_parsed`). Places come back as written ("Passo Manghen", never translated, never coordinates) and `resolve` geocodes them through `geocode.search_places` (biased by the resolved start), asks about same-named places further than `AMBIGUOUS_APART_M` apart, turns a duration into distance at the profile speed, and lists every `Question` to ask before generating — re-deriving "no start" itself rather than trusting the model, since a missing zone must never be skipped. The request text sits in `<request>` tags the system prompt calls data-only (a literal closing tag is defused). `llm.py` is one plain-`requests` client for the OpenAI-compatible chat API, so the model is config: a spec is `<provider>:<model>` (`openrouter`, `ollama_cloud`, `ollama`, `openai`; only the first colon splits, Ollama tags carry one), `NL_PARSER_MODEL` overrides the default (`ollama_cloud:gemma4:31b`, chosen on the eval set below, with `openrouter:google/gemini-2.5-flash` as the runner-up to fall back to), keys from each provider's env var (`OPENROUTER_API_KEY`, `OLLAMA_API_KEY`, …). Every call logs the requested and the *served* model plus tokens and cost (OpenRouter reports cost when asked with `usage.include`).
  - **Eval set** (`evals/route_parser/`): `cases.json` holds ~45 prompts in several languages (vague, unrealistic, conflicting, no zone, out of scope, injection) with expectations as `defaults` overridden per case — so an invented value loses its field — plus `any_of`/`contains` matchers and a per-case `ignore` for genuinely open readings. `run.py` scores every model on it (valid-JSON rate, field accuracy, all-fields-right rate, latency, cost/request), stops at `--max-usd` of reported spend, and writes every answer to the gitignored `results/`. `tests/test_route_parser_eval.py` checks each expectation is itself a valid `ParsedRequest` scoring full marks, so a case can't ask for something the schema can't say. Run with `uv run --env-file .env python evals/route_parser/run.py --model openrouter:<model> --model ollama_cloud:<model>`.
- `route_candidates.py` + `climbs.py` + `nl_routes.py` — step two: constraints → ranked routes, served by `POST /api/nl-routes/generate` (`nl_routes.py`'s router; form fields `text` and optional `lat`/`lon` map centre). Test-phase only — `require_feature("llm")` plus `require_same_origin` and its own `NL_ROUTE_REQUESTS_PER_WINDOW` bucket — and no frontend calls it yet. It answers `NlRoutesResponse` with exactly one of: `questions` (from `resolve`, asked before any routing), `infeasible` (with what to ask for instead), or up to `SHORTLIST` = 3 `options` best first, each with its routed `points` (what the planner would reopen), simplified `coords`/`elevations`, our metrics, its `misses` and an explanation. Road cycling only (`fastbike`). The same rule as the parser holds: **candidates are drawn geometrically and every number is ours.**
  - **Feasibility** (`check_feasibility`) runs before routing: distance outside `MIN`/`MAX_DISTANCE_KM`, more than `MAX_ASCENT_M_PER_KM` = 35 asked (ascent and the sum of wanted climb categories), and — once the start's elevation is known — a Cat 2+ wish with no known pass in reach high enough above the start (`RELIEF_SHARE` of the category's ascent). A Strava category is a score of length × gradient, which is just **100 × ascent**, so each category is a minimum ascent (`CATEGORY_MIN_ASCENT_M`: Cat 4 80m … HC 800m). Lenient on purpose: hard-but-possible still gets candidates.
  - **Planning** (`plan_candidates`, pure geometry): loops are circles of via points through the start (bearings, sizes, 3–4 points), or circles through the required points (named climbs, via places) at several sizes, plus an out-and-back over the climb as a relaxed-shape fallback, since many passes have no loop of the asked length on roads; A→B is direct with BRouter's alternatives 0–3 plus sideways detours when the target is longer; out-and-backs turn round at about half the distance on 8 bearings, or go **over the top** of a required climb (`_over_the_top`) rather than turning at the summit. A climb wanted by category is seeded from known passes (`find_passes` → `poi_db.query_pois_near_point("mountain_pass", …)`) whose height above the start best fits it. Generated points within `AVOID_RADIUS_M` of a place to avoid are dropped; main roads/ferries to avoid become BRouter options (`routing_options`); identical plans (sizes collapsing to the same circle) are routed once.
  - **Routing** is one `routing.route_via` call per candidate (all its points in one BRouter request, `alternativeidx` for alternatives), at most `MAX_CANDIDATES` = 10 per request, `ROUTING_WORKERS` = 3 in parallel, out-and-backs routed one way and mirrored. **Two rounds**: the first `FIRST_ROUND` = 4 measure how much longer the roads are than straight lines here (`observed_road_factor`, median, clamped — about 2 in the Dolomites against the default `ROAD_FACTOR` 1.3) and the start's elevation; the rest are planned with both (their ids get an `@<factor>` suffix). Near-duplicates (`DUPLICATE_SHARE` of one within `DUPLICATE_NEAR_M` of another, by a grid hash rather than `PolylineIndex`, whose fallback scan made this pathologically slow) are dropped. One candidate failing is skipped; a BRouter 429 stops everything and becomes a 429.
  - **Metrics** (`measure`): distance, ascent/descent (`geometry.elevation_gain_loss_m`, the frontend's 5m hysteresis), max gradient, climbs and difficulty (`climbs.py`), duration (`estimate_duration_h` = distance / 25 km/h + ascent / VAM, VAM from the account's `vam_m_per_h` else 700), surface shares and cycleway share from BRouter's surface runs, the share of a loop ridden twice (`repeated_share`), the named climbs actually passed (within `NAMED_CLIMB_HIT_M`), and water POIs — looked up for the shortlist only, since they don't affect ranking.
  - **Scoring** (`score`): a weighted sum of misses, each measured in range widths outside the asked range (`_range_miss`), weights in `SCORING_WEIGHTS` so they can be tuned with feedback. Every miss is kept as a `Miss` (constraint, wanted, got) so the answer can say which constraint was relaxed. Beyond the asked constraints, two defaults: `route_shape` when a different shape than asked is offered, and `road_gradient` when, with no gradient limit asked, the steepest **500m** (`ROAD_GRADE_WINDOW_M`) passes 20% — that's BRouter on a track; over 100m, DEM noise at mountain hairpins already reads 30% on a road that tops out at 15%.
  - **Explanations** (`explain`): one `llm.complete_json` call for the shortlist, fed only the computed facts (never the request text) in `<data>` tags, answering in the request's language; any option it skips, or all of them when it fails, gets `template_explanation`. It never fails the request.
  - **`climbs.py`** is a line-for-line port of the frontend's `lib/climbs.ts` (same constants, steps and road-cycling thresholds, hand-mirrored from `MAP_STYLES`), **kept in step by a shared fixture**: `tests/fixtures/climb_profile.json` is a 30 km profile with its expected climbs, asserted by both `tests/test_climbs.py` and `climbs.test.ts`, so changing one implementation alone fails a suite (regenerate the fixture only together with both). Its `route_max_grade_pct` takes an optional `window_m` the TS version doesn't have (for the 500m road check above).
  - Checked live (Gemma 4 parse, Photon, public BRouter, local PostGIS): "giro ad anello da Borgo Valsugana di 80 km con il Manghen" → 10 BRouter calls, ~12 s, every option over the Manghen; "da Trento a Bassano del Grappa, circa 100 km, evitando le strade principali" → 8 calls, all three options in range.
- **Accounts** (`auth.py`, `sessions.py`, `db.py`, `passwords.py`, `mailer.py`, `turnstile.py`, `migrations/`) — optional email + password accounts, self-hosted: no identity provider, no ORM, no auth library (`fastapi-users` was considered and passed over — maintenance mode, and it would bring SQLAlchemy plus an async driver alongside the psycopg pool already here). Accounts are for what needs a user (connecting other apps, test-phase features); everything else keeps working anonymously.
  - **Database:** `db.py` owns its own `DATABASE_URL` — a **separate database, `sulla_via`, on the same `postgis` server**, deliberately not inside `pois` (the POI import drops and rebuilds its table, and account data can be backed up/restored on its own). The FastAPI `lifespan` runs `db.init_database()`: `ensure_database` creates the database if missing (connecting to the `postgres` maintenance DB; created **from `template0`**, since an older volume's `template1` can carry a stale glibc collation version that makes Postgres refuse to copy it — this happened on the dev volume), then `apply_migrations` runs every `migrations/NNN_*.sql` not yet in `schema_migrations`, under an advisory lock. Postgres initdb scripts aren't used for this because they only run on a fresh volume. **Never edit a shipped migration — add a numbered one.** Init never raises: with `DATABASE_URL` unset or the DB unreachable, it logs, `db.is_ready()` stays false (retried at most every `RETRY_INIT_AFTER_S`), `/api/auth/me` reports `enabled: false` (the frontend then hides sign-in entirely) and every other account endpoint answers 503, while the rest of the app is unaffected.
  - **Sessions** (`sessions.py`): a random token in the HttpOnly, SameSite=Lax `sv_session` cookie, only its SHA-256 stored in `sessions`; 30-day expiry sliding forward on use (written at most hourly). Server-side rather than JWTs, so logout, a password reset and account deletion take effect at once. `Secure` comes from `COOKIE_SECURE` (on unless `"0"`), never the request's scheme — behind the Cloudflare tunnel the app only sees plain HTTP. CSRF: SameSite plus `require_same_origin` on every state-changing account endpoint, comparing `Origin` (or `Referer`) with `PUBLIC_BASE_URL`'s host, or the request's `Host` when that's unset — which is why Vite's dev proxy must **not** use the string shorthand (it sets `changeOrigin`, rewriting `Host` to `localhost:8000` so every POST is refused). Dependencies: `current_user_optional`, `require_user`, `require_verified_user`, and `require_feature(name)` — verified accounts whose `users.features` holds `name`, set by hand for a test phase (`UPDATE users SET features = array_append(features, 'llm') WHERE email = ...`).
  - **Not revealing who has an account** is a design rule, since sign-up is open: sign-up and forgot-password always answer 202 `{"status": "check_email"}` (an existing address gets an "you already have an account" email instead of a verification link; an unknown one gets nothing), a failed login is one generic 401 (`passwords.verify_password` spends a dummy Argon2 check for an unknown email so timing matches), and an email change to a taken address answers like a success. Consequently **sign-up doesn't sign you in — following the verification link does** (it proves the address first). Unverified accounts can still log in; `require_verified_user` is what gates.
  - **Name:** sign-up asks what to call the visitor (`users.name`, `migrations/003_user_name.sql`; 1–`MAX_NAME_LENGTH` = 60 characters after `_normalize_name` drops control characters and collapses spaces), editable via `POST /api/account/name`, and part of `AccountResponse` and the export. It's nullable — accounts made before it have none, and everything falls back gracefully (`_hello` opens emails with "Hi {name}," or "Hi,"; the frontend's `greeting()` likewise). Emails only ever use the account's **stored** name, never one typed into a form: a duplicate sign-up's "you already have an account" email greets the existing owner, not whoever typed the address. `sessions.USER_COLUMNS` carries it, and queries index their own extra columns past `USER_COLUMN_COUNT` rather than by number.
  - **Privacy acceptance:** sign-up requires `accept_privacy=true` (checked before anything else, captcha included) and records `users.privacy_accepted_at` + `privacy_version` (`auth.PRIVACY_VERSION`, the notice's "Last updated" date — bump it with `privacyConfig.ts`'s `LAST_UPDATED`; `migrations/004_privacy_acceptance.sql`), both in the export. The sign-up form's required checkbox ("I've read and accept the privacy notice") keeps "Create account" disabled until ticked. Accounts made before have null.
  - **Flows:** verify (24h link), resend verification, login/logout, forgot → reset (30-minute single-use link; only the newest link of a purpose works; resetting signs out every session and marks the email verified), change password (signs out every *other* session), change email (confirmed from the new address, old address notified), export (`GET /api/account/export`, a JSON attachment) and delete (password-confirmed; sessions and tokens cascade). Email-link tokens are single use and stored hashed in `email_tokens`.
  - **Passwords** (`passwords.py`): Argon2id with argon2-cffi's defaults, rehashed on login when those move; 10–256 characters, no composition rules (NIST 800-63B); `HIBP_CHECK=1` also refuses passwords in Have I Been Pwned's list via the k-anonymity range API (5-char SHA-1 prefix only, fails open).
  - **Email** (`mailer.py`): plain `smtplib` to any relay (`SMTP_HOST`/`SMTP_PORT` (465 = implicit TLS, else STARTTLS)/`SMTP_USER`/`SMTP_PASSWORD`/`MAIL_FROM`). Unset `SMTP_HOST` logs the message instead — how you follow links in dev. Links are built from `PUBLIC_BASE_URL`, never the request's `Host` (a forged Host would put another domain in a reset link); it's required once `SMTP_HOST` is set, and without both, the page's already-checked `Origin` is used.
  - **Captcha** (`turnstile.py`): Cloudflare Turnstile on sign-up and forgot-password. `TURNSTILE_SECRET_KEY` (runtime) turns the check on; the public site key is the `VITE_TURNSTILE_SITE_KEY` build arg. Both unset in dev and tests.
  - **Connections** (`connections.py`, `token_crypto.py`, `wahoo.py`, `migrations/002_connections.sql`): connecting Strava or Wahoo needs a **verified** account, and the tokens live in `connections` (one row per user and app), encrypted with Fernet under `TOKEN_ENCRYPTION_KEY` (runtime env, never in the repo or DB; a comma-separated list rotates keys, newest first — lose it and everyone must reconnect). Without a key, the authorize endpoints refuse up front (503) rather than after an OAuth round trip. **`connections.access_token(user_id, provider)` is the only way a token is used**: it refreshes within `REFRESH_BUFFER` (5 min) of expiry under `SELECT … FOR UPDATE`, so concurrent requests never spend one refresh token twice — which matters for Wahoo, which revokes the previous pair as soon as a refreshed one is used (the old browser-side cross-tab race is gone). If the app refuses the refresh, the row is deleted and the visitor sees "connect again". Expiry comparisons use the database's clock (`expires_at - now()`), as do sessions and email tokens, so host/DB clock skew can't distort them. `provider_http_error` maps every app failure to the response the frontend expects (401 reconnect, 429 + `Retry-After`, 503 not configured, else 502). **Wahoo** is now server-side too: the browser still makes the PKCE verifier and sends only its challenge to `GET /api/wahoo/authorize-url`, then the verifier with the code to `POST /api/wahoo/connect`; `WAHOO_CLIENT_ID` is runtime env (compose falls back to the old `VITE_WAHOO_CLIENT_ID`), `WAHOO_CLIENT_SECRET` optional. `wahoo.rename_route` re-reads the route first, since Wahoo's PUT requires position/distance/ascent on every update. Strava's granted scope arrives on the popup redirect, so `/api/strava/connect` takes it as a form field. **Disconnect** (`POST /api/connections/{provider}/disconnect`) revokes at the app (Wahoo caps unrevoked tokens) and forgets the row whatever the revoke did; **deleting the account** revokes every connection first (`revoke_all`). **Importing a browser-held connection** (`POST /api/connections/import`, from before accounts existed) takes only the refresh token, spends it at once — proving it's live, and for Wahoo revoking the browser's copy — and learns whose account it is from the app itself (Strava `get_athlete`, Wahoo `user_label`), never from the request. **Profile settings** (`GET`/`PUT /api/account/settings`, `user_settings` jsonb, `schemas.ProfileSettings`) hold per-activity speeds (`avg_speed_kmh`) and climbing speeds (`vam_m_per_h`, 100–2000, used only by the route generator so far — no input for it yet; the frontend's `ProfileSettings` type carries it so saving speeds doesn't drop it); the export includes connections (no tokens) and settings.
  - **Cleanup** (`cleanup.py`): a lifespan background task runs `run_once` at startup and every `CLEANUP_INTERVAL_S` (hourly): deletes expired sessions, spent or expired email links, and accounts never verified within `UNVERIFIED_ACCOUNT_TTL` (7 days; cascade takes their rows), and calls `rate_limit.prune()`, which forgets keys idle past `LONGEST_WINDOW_S` (otherwise an address that never returns stays in memory until restart, since `check_rate` only tidies a key it's using). Expiry is still enforced at use; this only bounds how long dead rows linger. Never raises, and runs without a database too (prune only). The visitor is told about the 7-day deadline: `AccountResponse.delete_unverified_at` (null once verified) drives the account menu's warning and a callout in settings, the verification email says so, and so does the "check your inbox" screen after sign-up. Sign-out already deletes the session row, so a copied cookie is refused at once. The account tests replace `cleanup.run_forever` with a no-op so a pass can't race them; `tests/test_cleanup.py` calls `purge_expired` directly.
  - **Tests:** `tests/test_auth.py` runs against a throwaway `postgres:16-alpine` testcontainer (skips without Docker, like `test_poi_db.py`), letting `init_database` create the database itself; mail is captured by monkeypatching `mailer.send_email`. The container and the `account_db`/`client`/`outbox` fixtures are shared through `tests/conftest.py` (one container per session), helpers through `tests/account_helpers.py`; `tests/test_connections.py` covers the stored-connection flows with Strava/Wahoo mocked by `responses`. Endpoint tests that don't need a database (`test_api.py`'s push tests, `test_strava.py`) override `sessions.require_verified_user` and monkeypatch `connections.access_token` instead.
- `ttl_cache.py` — the generic in-process TTL cache used by `routing.py` and `geocode.py` (reset between tests by `tests/conftest.py`).
- `gpx_io.py` — GPX parsing/merging via `gpxpy`, operating on bytes only (no filesystem I/O anywhere in the request path). Dedup of previously-added POIs works by stamping a custom `<extensions><waypointer:osm_id>` marker on GPX waypoints and checking for it on re-upload, with a proximity fallback for waypoints that lack the marker (hand-edited files, other tools) — this dedup is POI-type-agnostic, keyed only on OSM id/location. `discard_waypoints(gpx, indices)` removes pre-existing `<wpt>` entries by their position in the *original* upload's waypoint list (see `ExistingWaypoint.index` in `schemas.py`) — it must run before `add_waypoints` appends any newly selected candidates, since indices are only meaningful against the pre-discard order. `infer_poi_type(wpt)` best-effort classifies a pre-existing waypoint, in priority order: (1) a stamped `poi_type` extension marker (written by `stamp_poi_type`, used when the waypoint came from `fit_read.py`) wins outright; (2) else a stamped `osm_id` marker (a waypoint we ourselves previously added) → `"water"` (safe today since water is still the only auto-added type — revisit if that changes); (3) else substring-match the waypoint's `<sym>`/`<type>` text against each registered type's `sym_hints`; (4) else `"generic"`. Deliberately never matches against `<name>` — free-text names cause false positives (e.g. "Water Street Cafe").
- `fit_io.py` — builds a full ridable FIT course (not just isolated waypoints) using the `fit-tool` library. **A POI's icon on a Wahoo does not come from the standard FIT `course_point.type` enum** — reverse-engineering a real Komoot→Wahoo-generated FIT file (see `dev_tools/`) showed the icon is driven by a custom developer field named `course_point_type` (uint8), keyed per POI type in `poi_types.py` (e.g. `16` = water). This was later confirmed against the device for the full 0-99 range (`dev_tools/wahoo_poi_mapping.json`). The native `type` field is left as `CoursePoint.GENERIC` to match the confirmed-working reference file.
- `fit_read.py` — the inverse of `fit_io.py`: parses an existing FIT file (`fit_tool.FitFile.from_bytes`) into GPX bytes, used by `/api/wahoo/import-route`. `RecordMessage`s become one `GPXTrack`/`GPXTrackSegment`; `CoursePointMessage`s become `GPXWaypoint`s, each stamped with its recovered POI type (via the same developer field `fit_io.py` writes, looked up in `POI_TYPE_BY_COURSE_POINT_TYPE`, `"generic"` if absent/unrecognized) so `infer_poi_type` doesn't need to guess on next upload. fit-tool's position getters already return degrees, no semicircle conversion needed. Raises `ValueError` if the file has no positioned track points — a FIT with course points but no track isn't a usable route, and `main.py` surfaces that as a 400.
- `device_profiles.py` — small registry (`DEVICE_PROFILES`, not a plugin system) mapping a device key to just `{name, output_format}` (`GPX` or `FIT`) — two entries, `generic` and `wahoo_elemnt_roam_v3`. The format-specific values this used to hold directly (GPX symbol, FIT course_point_type) have moved into `poi_types.py`'s per-type registry now that POI types number in the dozens, not just water. `frontend/src/lib/devices.ts` mirrors it by hand, same convention as `poi_types.py`/`poiTypes.ts`; the frontend mirror is what each activity's `defaults.device` is checked against.
- `rate_limit.py` — in-memory per-IP sliding window, built by `make_rate_limit(bucket, budget, window)` and keyed on `(bucket, ip)` so each endpoint gets its own budget (all per `WINDOW_S = 60.0`): `/api/find-pois/route` (`REQUESTS_PER_WINDOW = 60`), `/api/find-pois/location` (`LOOKUP_POI_REQUESTS_PER_WINDOW = 30`), and `/api/route-leg` (`ROUTING_REQUESTS_PER_WINDOW = 60` — route planning is inherently chatty, since dragging an anchor re-requests its two adjacent legs, and sharing one budget would let a planning session starve the search it feeds), `/api/geocode` (`GEOCODE_REQUESTS_PER_WINDOW = 30` — the search box debounces 300ms, so this is a few typed searches per minute), `/api/poi-photos` (`PHOTO_REQUESTS_PER_WINDOW = 60`), `/api/map-pois` (`MAP_POI_REQUESTS_PER_WINDOW = 60` — fetched per viewport, debounced 400ms and only past a zoom, so this is panning rather than a fan-out), every `/api/strava/*` endpoint together (`STRAVA_REQUESTS_PER_WINDOW = 20` — they all spend this app's single Strava quota, shared by every visitor; also connection import and disconnect), every Wahoo call made with a stored token (`WAHOO_REQUESTS_PER_WINDOW = 30`), and `/api/nl-routes/generate` (`NL_ROUTE_REQUESTS_PER_WINDOW = 5` — each request is an LLM parse, about ten BRouter calls on the public instance and an LLM explanation). The find-pois budget is sized generously because the frontend fans one "Find POIs" click into one `/api/find-pois/route` call *per selected POI type* (see frontend section) rather than one combined call — this endpoint gets hit N times instead of once for the same amount of work, so the budget covers a full-registry search (~30 searchable types) plus a couple of re-searches within the window. The POI buckets just guard this app's own DB/CPU usage now that lookups hit local PostGIS; the routing and geocode buckets still protect shared third parties (BRouter's and Photon's public instances). The account endpoints use the same core, `check_rate(bucket, key, budget, window)`, keyed on something other than the IP too: login is limited per IP (`LOGIN_REQUESTS_PER_WINDOW = 10`/min) and per email (`LOGIN_ATTEMPTS_PER_EMAIL = 5` per 15 min, also spent by re-entering a password in settings), sign-up and forgot-password per IP (`SIGNUP_REQUESTS_PER_HOUR = 5`), anything that sends an email per destination address (`EMAILS_PER_ADDRESS_PER_HOUR = 3`, so the forms can't flood an inbox), and the rest per IP (`ACCOUNT_REQUESTS_PER_WINDOW = 60`). Single-process only, not meant to survive multiple workers/restarts. A 429 carries `Retry-After` (seconds until the window's oldest request ages out), which the frontend honours (see `lib/api.ts`). A 429 from BRouter or Photon upstream is passed on as a 429 with `Retry-After: UPSTREAM_RETRY_AFTER_S` (30) via `RoutingRateLimitedError`/`GeocodeRateLimitedError`, rather than a 502 — being throttled means back off, not "the service is broken".
- `schemas.py` — the Pydantic response/request shapes shared with the frontend's TS types: `Candidate` (carries `poi_type`), `PoiSearchConfig` (one entry per requested POI type + its max distance, sent as a JSON-string form field to `/api/find-pois/route`, same pattern as `/api/save`'s `selected_candidates`), `SearchRange` (an inclusive index range into the submitted route, narrowing **only** the PostGIS query — see `find_pois` above), `PoiLookupResult` (`/api/find-pois/location`'s response, carrying the element's full raw tag dict — kept separate from `Candidate`, which round-trips through `/api/save`), `ExistingWaypoint` (a pre-existing `<wpt>` from the uploaded file, tagged with its `index` in that file's original waypoint list and a best-effort inferred `poi_type` — editable client-side before it affects export), `FailedPoiType` (one requested type whose PostGIS query errored, `find_pois` returns a list of these instead of failing the whole request), `FindPoisResponse` (its `candidate_details` map carries each candidate's `osm_type`/`tags`/`last_edited` beside, not on, `Candidate`), `PoiPhotosResponse` (`PoiPhoto`s, link-only `PhotoLink`s, `failed_sources`), `RouteLegResponse` (one routed leg: index-parallel `coords`/`elevations` plus `distance_m`, its `surface` as a list of `SurfaceRunResponse` and `cycleway_m`), `PlaceResult` (`/api/geocode`'s per-place response: name, context, OSM kind, point, optional bbox), `AuthorizeUrl` (a connect popup's destination, either app), `ConnectionResponse` (provider, the app's display name for the account, granted scope — never a token), `WahooRouteResponse`, `ProfileSettings` (the account's settings document: `avg_speed_kmh` per activity key, validated), the account schemas `AccountResponse`/`AccountStatus`, and `StravaRouteResponse` (string `id`) `StravaActivityResponse` (string `id`, Strava's `sport_type`) and `StravaActivitiesPage` (one page of those plus `has_more`)
  (`frontend/src/types/candidate.ts` mirrors these by hand — keep them in sync manually when changing one side). `/api/save` and `POST /api/wahoo/routes` both accept `discarded_waypoint_indices` (JSON-string, defaults `"[]"`), `existing_waypoint_types` (JSON-string dict, defaults `"{}"`), and an optional `route_name`; `/api/save` alone also accepts `symbols` (JSON-string dict, poi_type → GPX `<sym>` override, defaults `"{}"`). `route_name` is kept separate from the sanitized output filename stem (`_safe_filename_stem` vs `_display_name` in `main.py`) so a user-typed name isn't mangled for filesystem safety before being shown as FIT `course_name`/Wahoo `route[name]`.

`dev_tools/` is exploratory tooling, not part of the shipped app: `generate_test_waypoints.py` builds a FIT file with all 100 `course_point_type` values laid out in a grid for manual on-device icon testing; `wahoo_poi_mapping.json` and `POIs.csv` are the resulting reverse-engineered value→icon mapping (cross-referenced against Strava/RideWithGPS/komoot's own POI category names) — this is the source of truth `poi_types.py`'s `course_point_type` values and `test_poi_types.py`'s assertions are checked against.

## Frontend architecture (`frontend/src/`)

- `App.tsx` owns all cross-cutting state via plain `useState` (no Redux/Context — intentionally, the tree is shallow). `selectedIds: Set<number>` is shared between `RouteMap` (map marker popups) and `CandidateChecklist` (the list) — both are just different views over the same state and call the same `onToggle`, which is what keeps map-popup and checklist selection in sync with no extra glue code. `keptWaypointIndices: Set<number>` is the equivalent for pre-existing waypoints from the uploaded file — defaults to "all kept" on every successful search, and `SaveCard` inverts it (kept → discarded) into the indices it sends to `/api/save`. `waypointTypeOverrides: Record<number, string>` holds the visitor's corrections to `infer_poi_type`'s guess for pre-existing waypoints (indexed by original waypoint index, applied on top of `existingWaypoints` via `useMemo`, survives a later re-search) — wired into both `ImportCard`'s waypoint list and `RouteMap` via `onChangeWaypointType`; there is no separate "assign waypoint types" dialog component, this is inline per-row editing via `PoiTypeCombobox`. `searchedPoiTypes` snapshots which POI types + distances were actually searched for at find-time, so `CandidateChecklist`'s per-type subsections (and their empty states) don't shift if the visitor tweaks step 2's inputs after results are already showing, without re-running the search. `clickAddedCandidates`/`clickAddedDetails` hold POIs added by clicking a basemap icon (via `/api/find-pois/location`), kept as siblings to `findResult` so a click works before any search or route exists; `allCandidates` merges the two — and resolves **one OSM element matching several searched types** through `poiTypes.ts`'s `mostSpecificPerElement`, so it's listed once under the most specific (`PoiTypeConfig.specificity`). It's a derived `useMemo` over the whole candidate list rather than an incremental merge, so dropping a type naturally restores the row the other type had lost. Other cross-cutting state: the account (`account`, `accountsEnabled`, `accountView`) and what comes with it through `lib/useAccountData.ts` — `connections` (keyed by account id, so signing out shows none without a reset) and the account's settings: on sign-in its speeds are written into the usual localStorage keys so `settings.ts` readers work unchanged, and `handleAvgSpeedChange` saves a change to the account too (debounced `SETTINGS_SAVE_DEBOUNCE_MS`); `mapStyleKey`, `hoveredPoi` (shared hover highlight between map and checklist, `{kind: "candidate" | "waypoint", id}`), `openStep` (accordion-style step-card open/closed state).
  - `handleFind` (the "Find POIs" button) is just `runFind(file, undefined)`. `runFind(targetFile, searchRange?)` fires one `findPois(file, [entry], searchRange)` call **per POI-type entry**, not one call carrying every type — staggered by `SEARCH_STAGGER_MS` (200ms) × index, smallest `max_distance_m` first, via `Promise.allSettled` (they still overlap in flight, just not at the same instant; the staggering predates the move off the public Overpass mirror to a local PostGIS DB and is kept mainly so results still stream in progressively per type, per `FindPoisCard`'s per-row status). Without a range, each type that's unchanged since the last search and didn't previously fail is skipped (`isAlreadySatisfied`, compared against `searchedPoiTypes`), surfacing an "already up to date" toast if nothing needed re-fetching. Results accumulate into a plain mutable object (not React state) pushed into `setFindResult` after each chunk resolves, so the map and checklist fill in progressively per type instead of waiting for the slowest one; a previously-failed or previously-missing type's completion/error status drives `FindPoisCard`'s per-row spinner/check/warning icon and its running `(done+errored/total)` count in the button label.
  - With a `searchRange` (the route planner's debounced re-search after an extend — `scheduleReSearch`, `RE_SEARCH_DEBOUNCE_MS`), `runFind` reuses `searchedPoiTypes` as its config rather than step 2's current inputs, never skips a type (the route changed), carries over **every** existing candidate, and merges each chunk in (a re-found `(osm_id, poi_type)` replaces the old one, since its distances were measured against the edited route). The range is resolved when the timer *fires*, not when scheduled: an appended leg starts as a straight-line placeholder and is replaced by routed geometry moments later, and only the untouched prefix is stable across that swap. Trims never re-search — the route only shrinks.
  - **Route planner state**: `plannerState` is non-null exactly while planning, and is then the source of truth for the route's geometry — one effect synthesizes `file` from it (`lib/gpx.ts`'s `buildGpxFile`, re-serializing from the imported `sourceDoc` so pre-existing `<wpt>` entries and their `waypointer:` markers survive), which is what keeps `/api/find-pois/route`, `/api/save` and the Wahoo push unaware the planner exists. A second effect fetches any leg still missing routed geometry (`pendingLegs`), de-duplicated via an in-flight ref and deliberately never cancelled (a leg is keyed on its own endpoints, so a late response is always either still wanted or a harmless no-op). An edit that would strand a checked waypoint/candidate further than `offRouteThresholdM` from the route is held in `pendingEdit` and confirmed via `OffRouteDialog`, which unchecks the stranded items on confirm (`trackedPositions` holds each tracked item's incremental distance — see `routePlanner.ts`). Every committed edit pushes the *previous* `PlannerState` onto `plannerPast` (capped at `PLANNER_HISTORY_LIMIT`), along with the keys that edit unchecked; `stepPlannerHistory` pops one entry, merges the current leg cache into it (so stepping back never re-fetches geometry), re-checks those keys, and unchecks whatever the restored route now strands — with a toast rather than `OffRouteDialog`, since the visitor asked for exactly that route back — recording them on the opposite stack so stepping back again re-checks them. Tracked positions are recomputed (`seedTracked`) rather than stored, which also covers candidates found since. Routed geometry arriving later (`withLeg`) is not a history step. Undo/redo, the selected point (`selectedAnchorIndex`, set by clicking any planner point including the green/red ends, which opens `RouteMap`'s `SelectedPointPopup` on it with the delete action (the popup is the only selection indicator — no ring on the marker) — deletion lives on the map, not in `PlannerPanel`; while a point is selected, a click elsewhere on the map only dismisses it rather than also appending a point) and any `pendingEdit` all reset per planning session (`resetPlannerSession`). Shortcuts (Ctrl/⌘+Z, Ctrl/⌘+Shift+Z or Ctrl+Y, Delete/Backspace on the selected point, Escape to deselect) are a window listener bound once per session via a ref, ignored inside inputs and dialogs. Edits without their own notion of what changed (deleting a point, undo/redo) use `commonPrefixLength` to re-search POIs only past the unchanged prefix, and not at all when the route merely shrank. Deleting points can take a route below two points, in which case the synthesizing effect clears `file`; "Done" with no route left behaves like "Remove route".
- `RouteMap.tsx` always renders (a MapLibre `Map` via `react-map-gl/maplibre`, with a neutral default view before any route is loaded) — the map is meant to be persistently visible, not conditionally mounted. Before `/api/find-pois/route` returns, it shows a route line parsed client-side (`lib/gpx.ts`, via the browser's `DOMParser`, no library) purely for instant visual feedback on import; once the backend responds, it switches to the backend's authoritative `route_coords` + candidate markers. POI candidates render as `Marker`s wrapping `lib/mapIcons.tsx`'s `CircleMarkerIcon` — the candidate's `poi_type` is looked up in `POI_TYPES` to pick its icon and color, with opacity distinguishing selected/unselected. Every coordinate in this codebase is `[lat, lon]`; `toLngLat` flips at the MapLibre boundary and nowhere else. Marker `onClick`s must call `e.originalEvent.stopPropagation()` or the click reaches the map's own handler in the same tick (which closes the popup that was just opened, and — while planning — would also drop an anchor). The route's start/end points get their own non-interactive `Marker`+`Tooltip` via `RouteEndpointMarkers` — green start, red end, collapsed into one marker when they coincide (loop routes). `RouteDirectionArrows` overlays arrowheads via a `symbol` layer with `symbol-placement: line`, re-registering its icon on every `styledata` event since swapping styles wipes custom images. Imperative map work is done in small `useMap()`-based child components (`FitBounds`, `BearingSync`, `PlanningCursor`, `BasemapPoiFilter`) with cleanup in the effect's return. The basemap's own POI icons (`BASEMAP_POI_LAYER_IDS`, filtered by `BasemapPoiFilter`/`lib/basemapPoiMapping.ts` to addable types) are made clickable via `interactiveLayerIds`; a click resolves the feature's own point geometry (not the click position, which may be on the label) through `onBasemapPoiClick` → `/api/find-pois/location`. Map cartography is switchable via `lib/mapStyles.ts`'s `MAP_STYLES` registry — `road_cycling` and `hiking` today; each entry also names the BRouter profile the planner uses (`routingProfileForStyle`), its `routingOptions`, an `icon` and its legend rows. Each entry carries a `buildStyle(theme)` that composes its finished MapLibre style (`lib/mapStyle/`) rather than naming a URL — read it through **`mapStyleFor(key, theme)`, which memoises per (activity, theme)**, so only the activity a visitor actually selects gets built (hiking's contours start a web worker and register a maplibre protocol, which shouldn't happen to someone who never leaves the bike map) and so the map and the legend are handed the identical object: `liberty.json` is OpenFreeMap's "liberty" vendored verbatim and never hand-edited (refresh it by re-downloading and re-running the style tests, which show what upstream changed), `houseStyle.ts` applies Sulla Via's own look to every activity (muted basemap and road palette, higher-contrast labels, tracks split into their own layers), and one module per activity applies only that activity's judgement — `roadCycling.ts` dims bike-prohibited and unpaved ways and highlights cycleways, `hiking.ts` never dims by surface (unpaved is the point on foot), dims by `foot` access instead of `bicycle`, always dims motorways and trunk roads whatever their tags say, and brings paths and tracks forward from zoom 11 — **paths in red**, the convention walking maps share (Swisstopo, CAI waymarks), and tracks in an earth tone, since a forest road is a vehicle way you happen to be walking on rather than a trail. The five path subclasses are told apart by **dash pattern** (`line-dasharray` takes a feature expression in this MapLibre version, so one layer covers all of them), and paved from unpaved by **lightness within the same hue** — a made path is still a path. It also adds what the base style buries or never draws: contour lines (`contours.ts` derives them in the browser with `maplibre-contour` from AWS Open Data's keyless terrain tiles, because OpenFreeMap's tiles carry no elevation whatsoever); fills for `landcover` `class=rock` (scree lighter, bare rock darker — liberty fills wood/grass/ice/wetland/sand and leaves rock blank, so its map goes empty above the treeline); and its own landmark layers for signposts, mountain huts and shelters (`hiking_poi`, filtered out of the `poi` source-layer rather than lifting `houseStyle`'s `icon-size: 0` suppression, which would bring back every restaurant) plus peaks and passes (`mountain_peak_point`/`mountain_saddle_point` — nothing in the base style references the `mountain_peak` source-layer at all). Icons come from OpenFreeMap's sprite keyed by the POI's `class`, which has no guidepost, hut, pass or viewpoint icon of its own, so those borrow generic ones for now. Terrain is driven by `hiking.ts`'s `TERRAIN_FILLS` table: the base paints landcover by `class` alone (every green is one green) and draws no farmland at all, so this adds scrub, grassland/meadow, farmland, scree and bare rock as separate flat tints, ordered so a narrower subclass layer draws over the broader class one it refines; forest keeps the base's own `landcover_wood`, recoloured. (Runtime-generated `fill-pattern` textures were tried and removed; OpenFreeMap's sprite has none of its own.) Hiking also **labels only the walking network**: `highway-name-major` is dropped and `highway-name-minor` narrowed to tracks, since road names crowd out the path name that actually matters and label ways the style is steering a walker away from. Its landmark layers are clickable (`HIKING_POI_LAYER_IDS` in `RouteMap`, kept separate from `BASEMAP_POI_LAYER_IDS` because those get the runtime "addable types only" filter and these carry their own), resolving through `basemapPoiMapping.ts` — guidepost → `info`, hut → `lodging`, peak → `summit` (which was a documented no-op until this layer existed). Shelters, wilderness huts and saddles are drawn but **not** clickable: no `poi_type` covers them, and adding one needs the full registry change plus a PostGIS reimport. Those same tiles carry neither `tracktype` nor `sac_scale`, which is why tracks can only be split by surface today (see the backlog card for the PostGIS route out of that). **Dark theme**: every patch module takes the theme and keeps a `LIGHT` palette plus a `DARK` twin with the same keys (all Tailwind steps); for dark, `darkBase.ts`'s `darkenBase` runs first on the cloned liberty (liberty → dark base → house → activity), flipping the OKLCH lightness of every colour literal in a `*-color` paint property so the base layers no patch touches go dark too — the one place map colours are computed rather than chosen from Tailwind. The dark background is opaque on purpose: light's translucent wash lets the page behind the canvas show through. `mapThemes.test.ts` checks both themes of every activity: opaque ground and water, streets standing off the ground more than buildings (buildings are a soft flat tone with no outline of their own, and a bridge takes its road's colours — only tunnels are dimmed), every map label with an opaque contrasting halo, and in dark every road lighter than the ground and no light sprite texture left (`road_area_pattern`/`landcover_wetland` become flat fills). Label colours come from `houseStyle.ts`'s exported `LABELS[theme]` roles (`strong` path names, `normal` streets/landmarks/`MapPoiOverlay`, `muted` POIs and contours, `water`, `halo`), shared by every module that draws a label. `compose.ts` holds the patch helpers (`setPaint`, `dimColorWhen`, `dimOpacityWhen`, `insertLayersAfter`, …), and throws on a patch naming a layer that doesn't exist rather than silently doing nothing. This replaced a hand-edited ~12k-line fork per activity (the parity test that pinned the composed cycling style to that fork has since been retired, along with the fork's drift it preserved); `hiking.test.ts` asserts the hiking judgements, that every activity's style passes MapLibre's own `validateStyleMin`, that no line layer is left without a colour (`houseStyle` inserts the track layers uncoloured on purpose, for each activity to colour), and that every layer in the walking network actually draws at the zoom its own `minzoom` advertises — a width ramp opening later than `minzoom` renders the layer invisible, which is a real bug this caught. The picker is `MapStyleSelect.tsx`, which is the content of the sidebar's first step rather than a control on the map, since the choice sets the whole session's activity (cartography + routing), not just the map's look. Its menu is `position="popper"`, trigger-width and `shadow-floating`, matching the sidebar's other two pickers (the POI type combobox and the place search) - Radix's default item-aligned placement overlays the menu on the trigger and reads as a different kind of control. - `lib/api.ts` — typed wrappers, one function per backend endpoint, all going through `request()` (also used by `wahooApi.ts`/`wahooAuth.ts`), which guarantees an `ApiError.message` is always fit to show the visitor as-is: an unreachable server becomes `NETWORK_ERROR_MESSAGE` (an abort is rethrown untouched), a 5xx becomes the caller's own `failed` message (the backend's 5xx `detail` carries raw exception text, so it's only `console.warn`ed), a 4xx shows the backend's `detail` — which is therefore written for the visitor wherever a visitor can trigger it (bad GPX file, unreadable Wahoo route) — unless `trustDetail: false` (third-party APIs), and a 401 uses `unauthorized` when given. - `lib/routePlanner.ts` — the route planner's model and edit operations; pure, no React or MapLibre, and the one part of the frontend with unit tests (`routePlanner.test.ts`, vitest, `npm test`). A route is an ordered list of **segments**, each either `fixed` (imported geometry, verbatim) or `routed` (a BRouter leg, geometry held in a cache keyed on `(from, to, profile)`). That makes drawing from scratch and editing an import the same feature: import → one `fixed` segment, trim → slice it (zero routing calls), extend → append/prepend a `routed` leg. `insertAnchorAt` splits the segment under a point; splitting a `fixed` segment yields two `fixed` halves whose concatenated geometry is **byte-identical** to before, which is what makes an imported route safe to start editing — only *moving* the new point re-routes, and only the two stretches either side of it (`moveAnchor` converts an adjacent `fixed` segment to `routed`). `removeAnchor` is the inverse: deleting an interior point merges its two segments — two `fixed` neighbours rejoin byte-identically (undoing an `insertAnchorAt` split with no routing), otherwise the merged stretch becomes one `routed` leg between the neighbours' own far ends (their `from`/`to`, not `plannerAnchors`' snapped points, so other legs keep matching their cache keys); deleting an end drops its segment, and is refused next to `fixed` geometry for the same whole-import reason as `moveAnchor`. `reorderAnchors` (the point-list drag) keeps, by identity, every segment whose two anchors stay consecutive in the same direction and makes every new pair a `routed` leg; it refuses any reorder that would break up a `fixed` segment (imported stretches keep their order), since on a pristine import that would replace the whole track. `plannerLegDistancesM` gives each segment's length for the list.

  **Dead-end spur removal**: a point dropped slightly off the road the route should follow (a few metres up a side street) makes BRouter route in to it and straight back out. BRouter's own `correctMisplacedViaPoints` can't help — it only fixes via points *inside* one request, and the planner routes one leg per request — so `segmentGeometries` does it on assembly: where routed leg *i*'s end and leg *i+1*'s start retrace the same road (`spurPointCount`, matching points within `SPUR_MATCH_M`, never cutting a leg below two points), and that stretch is no longer than the point's `spurToleranceM`, both are cut back to where they diverge — so the point's marker then sits there too. The tolerance is stored on the routed segment ending at that point, set by `appendAnchor`/`moveAnchor` from `spurToleranceM(zoom, latitude)` (`SPUR_TOLERANCE_PX` = 30px on the ground at the zoom the point was placed at; `RouteMap`'s `onViewChange` feeds `App.tsx`'s `mapZoomRef`), so a point placed zoomed out is forgiven a large spur and one placed zoomed in is kept as deliberate. Split and merge carry the tolerance of the point a segment still ends at. It never applies next to `fixed` geometry, isn't part of the leg cache key, and never modifies the cached legs; every consumer of segment geometry (`outboundGeometry`, `plannerAnchors`, `plannerLegDistancesM`, `insertAnchorAt`) goes through `segmentGeometries`, so distances measured on the drawn route and the model's segment lengths agree. A loop's return leg isn't spur-checked.

  **Route surface**: routed legs keep BRouter's `surface` runs and `cyclewayM` (`RoutedLeg`). `plannerSurface(state)` lays them end to end along `plannerGeometry`'s distance axis, each leg's runs scaled to its *drawn* length (spur removal can shorten it, and BRouter's distances differ slightly from the drawn polyline's anyway); `fixed` imported geometry and legs with no surface data count as unknown, a loop's return leg adds its own runs, and an out-and-back mirrors the outbound runs.

  **Elevation profile** (`ElevationProfile.tsx`, shown whenever there's a route with ≥2 points — planned or loaded, since knowing where the climbs are matters while picking POIs too): a collapsible strip floating over the bottom of the map, left of the sidebar (open by default on desktop, collapsed on phones), with the route's elevation against distance as a hand-rolled SVG (gaps where elevation is missing, hairline gridlines on rounded ticks, a tick per planner point, and no point marked until something is hovered — a highlighted peak read as a selected point; no chart library). The area and line are **coloured by gradient** in equal-length chunks, each by its own average gradient (at least `MIN_CHUNK_M` = 100m, and never narrower than `MIN_CHUNK_PX` on screen, so a long route isn't a blur of slivers); the tooltip reports the gradient of the chunk under the pointer, so the number always matches the colour. The five colours are fixed (`CLIMB_COLORS`/`DESCENT_COLORS`), but **where each band starts is per activity** — `MAP_STYLES`' `gradeScale` (`bandStartsPct` + `flatPct`, via `gradeScaleForStyle`), since 12% is a hard climb on a road bike and an ordinary mountain path: road cycling uses Wahoo's bands (green 0–4%, yellow 4–8%, orange 8–12%, red 12–20%, brown 20%+, flat within ±2%), hiking uses tens (0/10/20/30/40%, flat within ±5%), and the legend's edge labels are derived from the scale. Climbs use Wahoo's colour order as Tailwind steps spread in lightness so adjacent bands stay distinguishable, colour-blind readers included (green-600, yellow-500, orange-600, red-800, amber-950), and descents mirror the same bands as one blue getting darker with steepness (blue-400/500/600/800/950) — both validated with the dataviz skill's palette checker (`CLIMB_BANDS`/`DESCENT_BANDS`). Stretches strictly between −2% and +2% (`FLAT_GRADE_PCT`) are drawn in a neutral grey (`FLAT_COLOR`, neutral-400) rather than flickering between the gentlest climb and descent bands — grey, not black, so it recedes (a black flat band and a Wahoo-style climb-detection exception were both tried and rejected as flattening too much). Each chunk's colour comes from its own gradient only — an earlier version recoloured narrow pieces with their neighbour's colour, which cascaded along dense tracks and swallowed whole ±11% stretches. The fills use `crispEdges` so adjacent pieces don't leave anti-aliasing seams. Under the plot, on the same distance axis, a **surface band** (`plannerSurface`, below) in Tailwind palette steps that look like the surfaces themselves (paved `zinc-600` asphalt, cobbles `stone-500`, unpaved `amber-700` gravel/dirt, unknown a pale `zinc-200`); two legend rows underneath give the surface shares (+ the cycleway share) and the gradient scale. Its crosshair tooltip leads with elevation, then distance, gradient and surface. It's linked to the map in both directions through `lib/hoverDistance.ts` — a tiny `useSyncExternalStore` store rather than App state, because it changes on every pointer move and routing that through `App` would re-render the whole tree: hovering or arrow-keying the profile shows `RouteMap`'s `HoveredDistanceMarker` on the route, and hovering the route line (`RouteHoverReporter`, on the same wide hit layer as the line-drag) moves the profile's crosshair. `elevationGainLossM` (`lib/geometry.ts`) now ignores noise with a 5m hysteresis (`ELEVATION_NOISE_M`) — used for the profile header's figures and the difficulty — which deliberately differs from the backend's unfiltered `gpx_io.total_ascent_m`/`fit_io` FIT ascent (a follow-up, kept away from FIT changes that need checking on the device), so the app can read a little lower than a Wahoo for the same route.

  **Climbs and difficulty** (`lib/climbs.ts`, pure, `climbs.test.ts`): `detectClimbs` resamples the route's elevations every 25m (a missing elevation splits the route — nothing is measured across a gap), smooths over 75m, then walks it: a climb runs from the lowest point since the last one to its highest point, surviving a dip of up to max(10m, 10% of its ascent, capped at 40m) as long as it gets back above its top within 1km — a deeper dip or a longer flat ends it, and a level plateau doesn't extend it (a new high must be *strictly* higher). Each end is then trimmed while the 300m there is gentler than the activity's minimum, then step by step, so a false flat doesn't dilute the average. Per climb: length, ascent, average and max gradient (steepest 100m, the profile's chunk size), summit altitude, Strava's score (length m × avg %: Cat 4 ≥ 8,000 · 3 ≥ 16,000 · 2 ≥ 32,000 · 1 ≥ 64,000 · HC ≥ 80,000) and the Fiets index (also weighs the summit's altitude; kept beside the score to compare them in the Alps). What counts as a climb is per activity — `MAP_STYLES`' `climbRules` (`climbRulesForStyle`): cycling needs ≥ 3% and Cat 4's score and gets Cat labels, hiking needs ≥ 3% and 100m of ascent and gets none (a cycling convention). `routeDifficulty` rates a route Easy / Moderate / Hard / Very hard as the hardest of its criteria — total ascent, distance, steepest 100m (`routeMaxGradePct`) and, where categorized, its hardest climb — with thresholds in `MAP_STYLES`' `difficulty` (`difficultyForStyle`), and names the criterion that decided it. Checked against a BRouter route over Passo Manghen from Borgo (22.3 km, 1,660 m, 7.5%, HC; climbfinder: 22.9 km, 1,647 m, 7.2%). `App.tsx` computes both from the same `previewElevations` as the stats. The profile's header is the route's summary — distance, estimated duration, average speed, gain, loss, difficulty — readable while collapsed on a phone. The speed is a button (`SpeedControl`) opening a popover with the avg-speed input and how the duration is computed (Naismith's extra hour per 600m on hiking), so it can be changed with the profile folded. The difficulty has an info button whose tooltip (`DifficultyInfo`) names the deciding criterion and lists every criterion with its own level (`Difficulty.criteria`). Since a button can't hold another, the header row is a clickable `div` rather than the `CollapsibleTrigger`; the chevron is the real, focusable trigger, and the speed and info buttons and their popover/tooltip stop their clicks from reaching the row (React bubbles portalled clicks too). Climbs are bracketed and labelled above the plot ("Cat 2", or "Climb n" on hiking — a label may run past a short climb's bracket up to the next climb, falls back to just the category or number ("4", "HC", "5") when the full name doesn't fit there, and is left out only when even that doesn't; widths are estimated per character) over a faint band, listed in a legend row, and described in the crosshair tooltip; selected POIs are dots on the profile line in their type's colour, named by the tooltip when the pointer is near one. Outside the planner there are no point ticks, and the surface band and its legend row are left out when nothing is known about the surface (a loaded file), rather than drawn all "unknown" — a finished plan keeps its surface through `parkedPlan`. The route's invisible hit layer and `RouteHoverReporter` are now mounted for any route, not only while planning, so map↔profile hover works on a loaded route too (`isOnRouteLine`'s callers are all planning-only). The backend has a port, `climbs.py`, for the route generator — kept in step by a shared fixture (see `route_candidates.py` above).

  **Done keeps the plan** (`parkedPlan` in `App.tsx`): leaving the planner parks its `PlannerState` (and mode), and "Edit route" reopens that plan as it was — points, routed legs and their surface, shape, options — rather than rebuilding the finished file's coordinates as one `fixed` block (which lost all of that). It's dropped when the route goes: Remove route, importing another file, or restoring a draft. Reopened (like a restored draft) through `withCurrentRouting`, so a switch of activity in between routes with the current profile and sanitized options.

  **Draft across reloads** (`lib/plannerDraft.ts`): while planning, `App.tsx` saves the plan to localStorage (`"waypointer.plannerDraft"`, debounced `DRAFT_SAVE_DEBOUNCE_MS`) as a versioned `PlannerDraft` — the `PlannerState` with its leg cache pruned to the legs the route uses (`withPrunedLegs`; the cache otherwise keeps every drag position and option tried), the mode, the filename, and the *original* imported GPX serialized from `sourceDoc` (what the synthesizer re-serializes from, so an edited import's `<wpt>` entries survive). An empty plan isn't saved; a quota failure clears any older draft and shows a quiet note in `PlannerPanel` (`draftTooBig`). It's cleared on Done, on Remove route, on importing another file, and on Discard — never by the save effect. On load, a saved draft is offered back with a non-blocking toast (`lib/toast.ts` toasts can carry `actions`; those don't auto-dismiss) with Restore / Discard; `restoreDraft` reloads the source GPX through the same `loadGpxText` an import uses, re-derives tracked positions, and — since a draft may predate a profile switch or carry options the style no longer offers — routes with the current style's profile and `sanitizeRoutingOptions` (shared with `loadRoutingOptions`). Its saved routed geometry comes back with it, so only legs never fetched are requested again; `RouteMap`'s `fitRequest` frames the restored route (the map otherwise never refits while planning). A draft whose `version` isn't `DRAFT_VERSION` is ignored — bump it whenever `PlannerState` changes shape incompatibly.

  **Routing options** live on `PlannerState.options` and are part of every leg's cache key (`legKey(from, to, profile, options)`), so changing one (`setRoutingOptions`, `App.tsx`'s `handleRoutingOptionsChange` — one undoable edit, also saved as the style's preference) makes every routed leg pending and re-fetched, while `fixed` geometry is untouched and switching back or undoing is free from cache. While a leg is being re-routed, `segmentGeometry` draws the geometry it had under other options (`previouslyRoutedLeg`) rather than a straight line, so the route doesn't collapse and the off-route check doesn't measure against placeholders; only legs with no geometry at all (`unroutedLegs`) are dashed. The fetch effect passes the options a request was made with to `withLeg`'s `routedWith`, so a response arriving after the options changed is cached under its own key, not the current one. `RoutingOptionsSection.tsx` is the collapsible "Routing preferences" UI (choice → `Select`, toggle → `Checkbox`, header counts options changed from default).

  **Route shape** (`RouteShape`: `one-way` / `loop` / `out-and-back`, a field on `PlannerState`, switched via `setRouteShape` — which needs ≥2 points — and PlannerPanel's segmented toggle) says what comes after the last point. The return part is **derived, never stored**: `outboundGeometry` is the route as drawn, and `plannerGeometry` appends a loop's `returnLeg` (a virtual routed leg from the last anchor back to the start, fetched like any other since `pendingLegs` includes it; skipped when the ends are already within `ANCHOR_SNAP_M`) or an out-and-back's reversed outbound geometry (no routing). Anchors stay the outbound points only, which is why appending, deleting, reordering and moving need no shape special-cases — a new point automatically lands before the return. Trims measure and cut `outboundGeometry`; `plannerGeometry` (whole route as ridden) is what the map draws, what's exported, and what distance caps, stats and POI searches use. `removeAnchor` drops back to one-way below two points. In `App.tsx`, any edit to a loop/out-and-back goes through `applyEditWithFullReprojection` instead of the incremental trim/extend tracking, because the derived return changes with every edit so the old route is never a prefix of the new one; a line-drag grab past the outbound part maps to "append before the return" for a loop and to the mirrored outbound position for an out-and-back. A route that finishes where it starts (a planned loop/out-and-back, or any loaded route whose ends coincide) shows one combined start/finish marker (`START_FINISH_BACKGROUND`, a green/red split with a flag) instead of separate start/end markers; while planning, the last anchor is then an ordinary numbered point.

  What an endpoint drag does keys off `endpointNeighbourKind`, not off "imported vs drawn": next to a routed leg it moves, next to `fixed` geometry it extends or trims. That distinction exists because on a pristine import `segments[0]` spans the *whole* route, so treating a start-drag as a move would replace an 80km track with one routed leg. `moveAnchor` therefore still refuses an endpoint whose neighbour is fixed, and `App.tsx`'s `handleMoveEndpoint` routes those to `prependAnchor`/`appendAnchor`/`trimStart`/`trimEnd` instead.

  The anchor/segment indexing is load-bearing and easy to get wrong: `start` is held as its own field precisely so anchor 0 is `segments[0]`'s start and anchor *i* is `segments[i-1]`'s end and `segments[i]`'s start. The incremental distance updates are **exact, not approximate** — a trim only shrinks the route so distances can only increase (only points whose nearest segment was removed need recomputing), and an extend only grows it so distances can only decrease (measure against the new legs alone and keep the smaller). The tests assert these equal a full recompute; they caught five real indexing bugs when first written.

- `lib/analytics.ts` (constants factored out into `lib/analyticsConfig.ts`) wraps Umami Cloud's `window.umami.track(event, properties)` global behind a typed `track()` that no-ops (never throws) if the script never loaded — unset `VITE_UMAMI_WEBSITE_ID`, an ad-blocker, or a self-hosted deployment that opts out — so callers never need to guard for its absence. The script is injected imperatively from `main.tsx`'s `initAnalytics()` rather than a static `<script>` tag in `index.html` like Tally's, specifically so an unset website id means *zero* network calls to Umami (unlike Tally, which has no meaningful "off" state to guard). `VITE_UMAMI_WEBSITE_ID` follows the same non-secret build-arg pattern as `VITE_TALLY_FORM_ID` and `VITE_TURNSTILE_SITE_KEY` (Dockerfile/docker-compose.yml) — leaving it unset is the supported way to ship the RPi/LAN deployment with no analytics at all. Individual POI/waypoint checkbox toggles are deliberately **not** tracked — exploratory clicking on a route with many candidates could burn through Umami's free-tier 100k events/month for little analytical value — only aggregate counts at `find_pois_run`/`route_saved`/`route_sent_to_wahoo` checkpoints (`selected_candidate_count`, `present_poi_types`), which is enough to derive selection behavior without per-click noise. The route planner follows the same checkpoint rule (`App.tsx`): `route_planning_started` (`mode` new/edit, `from` fresh/place/reopened/draft), `route_shape_changed`, `routing_options_changed` (one per changed option), and `route_planning_done` on "Done" — point count, distance and the same filtered ascent/descent the app shows, shape, style, and every routing option as `opt_<name>`. Its `points` are the planner points rounded to 2 decimals (~1km, `ANALYTICS_POINT_PRECISION`) and sent as one Google encoded polyline (`lib/polyline.ts`; decode with precision 2) — the rounding is a deliberate privacy choice, since a route's start is often someone's home and Umami is a third party, and the encoding is what fits 50 points into Umami's 500-character string limit (an oversized one is dropped rather than cut, since a truncated polyline decodes to wrong points). Umami also caps an event at 50 properties and numbers at 4 decimals, so distances are sent in whole metres. The place search sends `place_search_picked` and `place_added_to_route` (`where` start/end, `source` pin/list) with the place's name and OSM kind — never the typed query. Undo/redo, point edits and hovers aren't tracked.
